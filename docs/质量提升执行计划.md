## 1 阶段 0 —— 先造尺子（半天，**不可跳过**）

> 原文 §8 把评测集排在第 9 步。这里提到第一步，理由一句话：
> **没有基线，"提升"就只是主观感受；而主观感受正是当前这个 bug 能活这么久的原因**——
> 摘要被整场丢光返回"看起来正常但很差的本地规则输出"，不报错、不告警，靠肉眼根本发现不了。

| # | 事项 | 做法 | 验收 |
|---|---|---|---|
| 0-1 | 建评测集 | `docs/verification/quality/` 下放 5 场：超短误录（≈25 s）/ 25 min / 45 min ×2 / 90 min。直接从数据根历史会话导出，**不重新录音** | 5 个 `session.json` + 手写金标准 |
| 0-2 | 指标脚本 | 复用已归档的 `docs/verification/quality-lab/`（`compare` / `postprocess` / `prompt_ab` / `verify`），收敛成一个 `quality_report.py`，输出方案 §5.1 的 13 项指标 | 一条命令出表格 |
| 0-3 | **跑基线** | 用**当前代码**（未改任何东西）跑一遍 5 场，把 13 个数字存进 `baseline.json` | 有可 diff 的基线 |

- 唯一需要你本人花时间的是 **0-1 的金标准**（每场人工写一份"理想纪要"，约 30 min/场）。
  这是整个计划里最值钱的 2.5 小时——它把后面的每一步从"我觉得好些了"变成"覆盖率 62% → 84%"。
- 脚本要能对**未改动的 App** 取数：优先直接读会话 `session.json` 里的 `analysis`；需要跑模型时走
  `MS_E2E_KEY` 环境变量门控（照抄现有临时 XCTest 模式，无 key 即跳过）。

**阶段 0 的出口信号**：`python quality_report.py --baseline` 能打出 13 行数字，其中至少
`finish_reason` 一列是 `length`——这条就是你"一开会就觉得内容很差"的病历。

## 1.5 阶段 0 执行结果（2026-09-13 已完成）

### 现状基线（未改动的代码，5 个 case 全跑完，0 失败）

| 指标 | 目标 | 现状（中位 / 最差） | 判定 |
|---|---|---|---|
| 速览字数 | 250 ~ 500 | 231 / 181 | 未达 |
| 纪要字数 | ≥ 1200 | 940 / 651 | 未达 |
| 纪要小标题 | ≥ 3 | 6 / 4 | 达标 |
| 空话动词 | = 0 | 4 / 6 | 未达 |
| 决策条数 | ≥ 12 | 7 / 2 | 未达 |
| 待办条数 | ≥ 10 | 6 / 1 | 未达 |
| 带 owner 的待办 | ≥ 30% | 0% | 未达（字段都没有） |
| 有标点段占比 | ≥ 98% | 29% / 10% | 未达 |
| 段数 / 原始段数 | ≤ 25% | 100% / 100% | 未达（后处理未做） |
| 总字数保留率 | ≥ 95% | 100% | 达标 |
| 空态 case | 干净空态 | 产出 9 处元评论 | 未达 |

**11 项里 2 项达标、9 项未达。**

「纪要小标题」这条要留个心眼：它现状就达标，但最初的正则只认 markdown `#`，
而基线用的是「一、二、」中文序号，于是被误报成 **0**。
**指标口径错会把人带去修没坏的东西**——核对口径和看数字同样重要。

### 顺带查实的四件事

**① 长会那次失败是测试环境的锅，不是 App 的 bug。**
首轮 `long-full`（44.7 分钟）报 `networkFailed`、耗时 83.7 s，报错「HTTPS 安全连接失败」。
去掉沙箱代理直连重跑 → **60.2 s 成功**。归因：沙箱代理掐断了长流式连接。
但有真实的旁证价值：**任何会掐长连接的代理 / VPN（用户本机的 FlClash 同理）
都会让长会请求失败**，而 App 现在会把它变成一份"看起来正常但很差"的本地规则输出——
和截断是同一种病。P0-3 的「降级要可见」应把这类网络失败也覆盖进去。

**② 标点塌陷发生在 13 分钟之后，而 P0-2 的 A/B 测在了没问题的区间。**
按 60 秒粒度复查整场：`0–13 min` 多数时间 **100%**，`20–40 min` 大量为 **0%**，
中间只在 37 min、40 min 短暂回弹。而 P0-2 依据的那组 A/B 跑的是 `0~604 s` ——
**恰好是本来就没问题的那一段**。已在方案 §4 P0-2 加勘误：落地前必须补测
`780~1384 s`（已塌陷窗口）。机制上讲得通（whisper 的 initial prompt 只作用于首个解码窗口，
之后解码器以自己退化的输出为上下文），但**机制成立不等于效果已证**。

**③ 复读才是转写侧的大头，低置信垃圾段几乎可以忽略。**
`871` 段里 **91 段（10.4%）**处在复读串里，最长一串是同一句重复 **86 次**
（「这两天让他们去信息」）；而「置信度 <0.30 且字数 <8」的垃圾段只有 **5 段（0.6%）**。
→ **P0-1 内部优先级要调整**：复读折叠 ≫ 按句合并 > 去低置信。
用户说"转写效果不好"，很可能有一部分就是看到同一句话刷了 86 行。

**④ P1-5 的必要性被实测证实。** `too-short`（26 秒误录）产出 9 处元评论，原话：

> 「本次输入材料中不包含任何工作会议内容。全文只有一句栏目宣传语……」并以
> 「## 材料情况说明 / ## 处理建议」为小节写了 205 字纪要。

### 素材缺口（脚本会打印，不掩盖）

| 缺口 | 影响 |
|---|---|
| 最长逐字稿 13 037 字符 < 分章阈值 24 000 | **分章路径零覆盖**，P2-4 做完也验证不了；需要一场 >60 分钟的会 |
| 无人工金标准 | 「覆盖度」这一维不可算；其余客观指标不受影响 |
| 数据根只剩 2 场会话 | 评测集靠长会切片凑出 5 例，样本面偏窄 |

### 本轮交付

- `Scripts/build_eval_set.py`　只读导出评测集（长会切片 + 超短误录），素材不足如实报缺口
- `Scripts/quality_report.py`　13 项客观指标，`--write-baseline` / `--diff`
- `Scripts/quality_report.sh`　一条命令出报告
- `Tests/MeetingScribeTests/QualityEvalTests.swift`　直接调 App 自己的引擎跑评测，
  `MS_E2E_KEY` 门控（无 key 自动跳过），`MS_QUALITY_CASES=` 可只跑指定 case
- `docs/verification/quality/README.md`　评测集说明

**隐私处理**：评测集是从真实会议导出的逐字稿，`cases/` `runs/` `baseline.json` 全部 gitignore，
只提交脚本与说明。代价是 CI 跑不了这套指标——阶段 3 若要进 CI，得另造一份合成语料。

## 2 阶段 1 —— P0 止血（1 天）

四个子任务之间的真实关系（原文 §8 只给了顺序，这里给依赖）：

```
1A 预算与截断 ──┐
                ├── 必须同批（只改 prompt 不改预算 = 0 字正文，见方案 §2.4 B 组）
1B 两段式 prompt ┘

1C 逐字稿后处理 ── 独立，纯函数
1D 转写参数 ────── 独立，但 1C+1D 一起评测更准
                  （标点变好 → 后处理的分句边界更准，两者互相加成）
```

| 顺序 | 事项 | 动哪些文件 | 验收 | 回滚 |
|---|---|---|---|---|
| 1A | `analysisTokenBudget` 16k→32k、`chapter` 8k→16k、`escalationCap`→48k；`finish_reason == "length"` **即**判截断并翻倍重试；`parseAnalysis` 宽容解析 | `SummaryEngine.swift` | 5 场 `finish_reason` 全 `stop` | 改常量，一行回退 |
| 1B | 两段式 prompt（速览 24k / 纪要 16k），**删掉"不要重复列出决策与待办"那句** | `SummaryEngine.swift:299-340` | 速览 ≥250 字且 ≥2 条含数字/日期；纪要 ≥1200 字、≥3 小标题、空话动词 0 | 旧 prompt 文本留注释块 |
| 1C | 新增 `TranscriptCleaner`。**内部优先级按阶段 0 实测调整：复读折叠 ≫ 术语替换 > 按句合并 > 丢低置信**（复读占 10.4% 段，垃圾段仅 0.6%） | 新增 `TranscriptCleaner.swift` + `Tests/`，调用点在 `WhisperTranscript.init` 之后 | 段数 ≤ 原始 25%、总字数 ≥95%、抽 10 段无语义断裂 | 纯新增，删文件即回滚 |
| 1D | 加 `-sns` / `--carry-initial-prompt` / `--prompt` 拼术语表（先硬编码一版） | `WhisperPipeline.swift:327-357`、`:324` 注释要改写 | 有标点段 ≥98%、抽 10 个专名数命中率 | 删三个参数 |

### 阶段 1 的两个工程细节（原文没写，但会咬人）

**① 两段式会翻倍调用次数 → 用并发抹平延迟。**
一次改为两次请求，45 min 会议若串行，用户等待时间翻倍。两条请求之间**没有依赖**，
用 `async let` 并发发出，总耗时 ≈ `max(速览, 纪要)` 而不是 `sum`。改完实测一次端到端延迟，
写进提交信息。

**② 宽容解析要有边界，否则会把幻觉当结果收下。**
只在**确认截断**（`finish_reason == "length"`）时启用宽容解析；同时把"本次结果不完整"
作为可见状态带到 UI（复用现有 `summaryError` / 提示位），而不是静默收下一份半截纪要。
宽容解析的收益是"救回已完整的字段"，不是"容忍坏 JSON"。

**阶段 1 的出口信号**：5 场里速览/纪要**都不为空**，且第 0 阶段那列 `length` 变成 `stop`。
这一步做完，产品从"不可用"跨到"可用"——是本计划里唯一一次**性质变化**，其余都只是优化。

## 3 Gate A —— P0 完成后的决策门（**回答"下一步做什么"**）

P0 跑完不要直接开工 P1。先花 20 分钟看阶段 0 那张表的 diff，按下表分流：

| 观察到的现象 | 说明什么 | 下一步 |
|---|---|---|
| 13 项指标基本达标（速览/纪要字数、小标题、空话、专名） | 主因确实是"截断+prompt"，已修好 | **进阶段 2（P1）** |
| 内容不再为空，但**废话多、抓不到重点** | prompt 措辞还不够狠，或材料本身太散 | 先只迭代 1B 的 prompt（成本最低、当天可验），达标再进阶段 2 |
| 纪要**信息密度够但张冠李戴**（幻觉） | 忠实度问题，属另一类缺陷 | **暂停推进**，先做 §5.2 的 LLM 裁判「忠实度」维，定位是把原文写歪还是补了原文没有的事实 |
| 专名命中率仍 <90%（1D 没救回来） | 术语表不够全，或音频质量是瓶颈 | 把 **P1-3 术语表 UI** 从阶段 2 提到最前（用户自己加词比任何模型都准） |
| 仍然 `length` 截断 | 预算/模型侧还有未发现的消耗 | 回到方案 §2.4 重测，别往下做功能 |

> **判断口径**：Gate A 是一次"要不要继续投"的体检，所以看的是**主因是否被解决**，
> 不是看数字有没有变好。若主因解决、只剩细节，就该进 P1；
> 若主因没解决，往下做 P1 等于在坏地基上装修。

## 4 阶段 2 —— P1 让产出"看得见"（2~3 天）

P0 解决"有没有内容"，P1 解决"内容用户看不看得进去"。**必须先 2A 再 2B**：
数据模型没字段，页面渲染不出来。

| 顺序 | 事项 | 依赖 | 动哪些文件 | 验收 |
|---|---|---|---|---|
| 2A | 加字段：`ActionItem.owner`、`MeetingAnalysis.headline` / `overviewBullets` / `openQuestions` | 1B | `MeetingModels.swift` | **老会话仍可解析**（`decodeIfPresent` + 默认值，抄现有手写 init） |
| 2B | 速览页重做渲染：一句话结论 / 要点（时间锚可点跳播放）/ 决策摘要 / 待办摘要（含 owner）/ 时间轨 | 2A | `WorkbenchView.swift`（`WorkbenchOverviewDocument`） | 一屏内看到"结论 + 要点 + 谁做什么" |
| 2C | 材料不足前置门禁：有效字数 <200 或有效段 <5 → 不调模型，走专用空态 | 无 | `SummaryEngine.analyze` 入口 + UI 空态 | 25 s 误录不再出现"本次材料仅包含…"式元评论 |
| 2D | 设置页「识别术语表」（一行一词，逗号分隔别名），同一份数据接三处：`--prompt`、后处理替换表、事后纠错 | 1C、1D | 设置页 + `UserDefaults` | 加词后重跑，错词减少 |
| 2E | 逐字稿可就地编辑（双击）+ 一键重整理，校正后标记该场 | 无 | `WhisperPipeline` / 原文页 | 用户能自己改错词，不必靠模型反复重试 |

顺序建议 **2A → 2B → 2C → 2D → 2E**：前两项是用户最能直接感知的收益，也最容易被验收；
2C 是纯增益且改动小，可随时插入；2E 略重（涉及写回与状态标记），放最后。

**UI 类改动一律走既有纪律**：改完用 `macos-ui-pixel-verify` 取窗前截图 + 像素扫描，
并用 Vision OCR 复核折行/截断（几何对 ≠ 渲染对）。

**阶段 2 的出口信号**：不点开任何二级页面，一屏就能回答"这次会定了什么、我该做什么"。

## 5 阶段 3 —— 把度量固化（1 天）

到这一步，`quality_report.py` 已经在手上了，别再让它只活在 `/tmp` 或 `docs/` 里：

| # | 事项 | 验收 |
|---|---|---|
| 3-1 | 指标脚本固化为 `Scripts/quality_report.sh`，README 写一句用法 | 一条命令出 13 项指标 |
| 3-2 | 客观指标进 CI（**不依赖网络的子集**：段数/字数/小标题数/空话动词），模型相关项保持本地手动 | CI 能拦住"段数回退""空话复现"这类退化 |
| 3-3 | LLM 裁判脚本（§5.2 四维：忠实度/覆盖度/信息密度/可执行性），用**不同厂商**模型当裁判 | 人工抽检变成一条命令 |

> 顺序理由：3-2 的 CI 化必须放在阶段 2 之后——UI/模型字段还在动，过早固化会不断改测试。
> 但 3-1 的脚本本身在阶段 0 就该有。

## 6 Gate B 与阶段 4 —— P2 按触发条件做，不按排期做

P2 每一项都改变产品形态或引入新变量，所以**不给日期，给触发条件**。跑完阶段 2、阶段 3 后，
看指标决定该动哪一项：

| 触发条件（指标） | 该做的 P2 | 代价 | 备注 |
|---|---|---|---|
| 待办 **带 owner 占比 <30%**，纪要答不出"谁做什么" | **P2-2a 双声道录音**（mic 左 / system 右） | 小 | 只解决"我方 vs 对方"，但这是会议里最值钱的一刀；同时给 `TranscriptSegment` 预留 `speaker` 字段 |
| 用户开始按「周会 / 客户会 / 评审会」提不同要求 | **P2-3 会议背景输入**（参会人 + 会议类型一句话指引） | 小 | 先加一句方向指引，**不做 4 套模板** |
| 逐字稿碎裂仍是主要抱怨，且 1D 已生效 | **P2-1 VAD 调参**（实验性，开关默认**关**） | 中 | 必须先把 `--vad-min-silence-duration-ms` 从 100 调到 ≥800；**即便调参，1C 的后处理仍必须做** |
| 长会议（>60 min）走分章路径，综合材料有"章节摘要：/明确结论："噪声 | **P2-4 分章模板噪声** | 小 | 改成只输出纯文本摘要，综合阶段统一抽决策/待办 |
| 需要区分 3 人以上的具体发言人 | **P2-2b/c**（pyannote / 手工标注） | 大 | b 需引入 Python 运行时，与"纯本机 Swift"定位冲突，建议优先 c（手工标注后重整理） |

**没有触发条件命中，就不做 P2。** 方案 §7 已列了 6 项明确"不做"的想法，
其中"换更强的云端模型""换更大的总结模型""引入 RAG"这三项在 P0 达标后依然不成立——
理由都在 §6/§7，不重复。

## 7 风险登记册

| 风险 | 触发概率 | 影响 | 缓解 |
|---|---|---|---|
| 只改 prompt 不改预算 → **0 字正文**（比现状更差） | 高（若 1A/1B 拆批） | 高 | **1A 与 1B 同一提交**；提交前用 5 场跑一遍确认 `stop` |
