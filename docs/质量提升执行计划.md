## 1 阶段 0 —— 先造尺子（半天，**不可跳过**）

> 原文 §8 把评测集排在第 9 步。这里提到第一步，理由一句话：
> **没有基线，"提升"就只是主观感受；而主观感受正是当前这个 bug 能活这么久的原因**——
> 摘要被整场丢光返回"看起来正常但很差的本地规则输出"，不报错、不告警，靠肉眼根本发现不了。

| # | 事项 | 做法 | 验收 |
|---|---|---|---|
| 0-1 | 建评测集 | `docs/verification/quality/` 下放 5 场：超短误录（≈25 s）/ 25 min / 45 min ×2 / 90 min。直接从数据根历史会话导出，**不重新录音** | 5 个 `session.json` + 手写金标准 |
| 0-2 | 指标脚本 | 复用已归档的 `docs/verification/quality-lab/`（`compare` / `postprocess` / `prompt_ab` / `verify`），收敛成一个 `quality_report.py`，输出方案 §5.1 的 13 项指标 | 一条命令出表格 |
| 0-3 | **跑基线** | 用**当前代码**（未改任何东西）跑一遍 5 场，把 13 个数字存进 `baseline.json` | 有可 diff 的基线 |

- 唯一需要你本人花时间的是 **0-1 的金标准**（每场人工写一份"理想纪要"，约 30 min/场）。
  这是整个计划里最值钱的 2.5 小时——它把后面的每一步从"我觉得好些了"变成"覆盖率 62% → 84%"。
- 脚本要能对**未改动的 App** 取数：优先直接读会话 `session.json` 里的 `analysis`；需要跑模型时走
  `MS_E2E_KEY` 环境变量门控（照抄现有临时 XCTest 模式，无 key 即跳过）。

**阶段 0 的出口信号**：`python quality_report.py --baseline` 能打出 13 行数字，其中至少
`finish_reason` 一列是 `length`——这条就是你"一开会就觉得内容很差"的病历。

「纪要小标题」这条要留个心眼：它现状就达标，但最初的正则只认 markdown `#`，
而基线用的是「一、二、」中文序号，于是被误报成 **0**。
**指标口径错会把人带去修没坏的东西**——核对口径和看数字同样重要。

### 顺带查实的四件事

**① 长会那次失败是测试环境的锅，不是 App 的 bug。**
首轮 `long-full`（44.7 分钟）报 `networkFailed`、耗时 83.7 s，报错「HTTPS 安全连接失败」。
去掉沙箱代理直连重跑 → **60.2 s 成功**。归因：沙箱代理掐断了长流式连接。
但有真实的旁证价值：**任何会掐长连接的代理 / VPN（用户本机的 FlClash 同理）
都会让长会请求失败**，而 App 现在会把它变成一份"看起来正常但很差"的本地规则输出——
和截断是同一种病。P0-3 的「降级要可见」应把这类网络失败也覆盖进去。

**② 标点塌陷发生在 13 分钟之后，而 P0-2 的 A/B 测在了没问题的区间。**
按 60 秒粒度复查整场：`0–13 min` 多数时间 **100%**，`20–40 min` 大量为 **0%**，
中间只在 37 min、40 min 短暂回弹。而 P0-2 依据的那组 A/B 跑的是 `0~604 s` ——
**恰好是本来就没问题的那一段**。已在方案 §4 P0-2 加勘误：落地前必须补测
`780~1384 s`（已塌陷窗口）。机制上讲得通（whisper 的 initial prompt 只作用于首个解码窗口，
之后解码器以自己退化的输出为上下文），但**机制成立不等于效果已证**。

**③ 复读才是转写侧的大头，低置信垃圾段几乎可以忽略。**
`871` 段里 **91 段（10.4%）**处在复读串里，最长一串是同一句重复 **86 次**
（「这两天让他们去信息」）；而「置信度 <0.30 且字数 <8」的垃圾段只有 **5 段（0.6%）**。
→ **P0-1 内部优先级要调整**：复读折叠 ≫ 按句合并 > 去低置信。
用户说"转写效果不好"，很可能有一部分就是看到同一句话刷了 86 行。

**④ P1-5 的必要性被实测证实。** `too-short`（26 秒误录）产出 9 处元评论，原话：

> 「本次输入材料中不包含任何工作会议内容。全文只有一句栏目宣传语……」并以
> 「## 材料情况说明 / ## 处理建议」为小节写了 205 字纪要。

### 阶段 1 的两个工程细节（原文没写，但会咬人）

**① 两段式会翻倍调用次数 → 用并发抹平延迟。**
一次改为两次请求，45 min 会议若串行，用户等待时间翻倍。两条请求之间**没有依赖**，
用 `async let` 并发发出，总耗时 ≈ `max(速览, 纪要)` 而不是 `sum`。改完实测一次端到端延迟，
写进提交信息。

**② 宽容解析要有边界，否则会把幻觉当结果收下。**
只在**确认截断**（`finish_reason == "length"`）时启用宽容解析；同时把"本次结果不完整"
作为可见状态带到 UI（复用现有 `summaryError` / 提示位），而不是静默收下一份半截纪要。
宽容解析的收益是"救回已完整的字段"，不是"容忍坏 JSON"。

**阶段 1 的出口信号**：5 场里速览/纪要**都不为空**，且第 0 阶段那列 `length` 变成 `stop`。
这一步做完，产品从"不可用"跨到"可用"——是本计划里唯一一次**性质变化**，其余都只是优化。

> **新增口径勘误（本轮踩的，与 §1.5 的"小标题"同一类）：**
>
> ① **空话动词不能用裸词匹配**。复核时发现 slice1 被判 2 处空话，实际是
> 「后续给用户表现的形态也要**围绕**问答、视频和远程协助**展开**」—— 这是**实质内容**。
> 空话的真形态是**句首起兴**（`本次会议围绕 X 展开`），已改成句式匹配。

>
> ② **`段数/原始段数 ≤ 25%` 只对"本来就很碎"的转录有意义**。slice1 的原始转写
> 本来就是句子级（10.6 段/分钟、94% 带标点），**没有可折叠的碎片**，比值自然接近 1 ——
> 那是指标不适用，不是后处理没生效。达标判定已限定在**病态密度（≥15 段/分钟）**的 case 上，

### 1D 补测结果——闭合「转写参数效果不可见」这个缺口

（同一段音频、其余参数全同，只动 1D 那三个变量）：

**① 塌陷确实存在，而且就在这个窗口。** A 臂按 2 分钟分桶一路是 0~8%，
症状形态也对得上：**248 段、段均 11.2 字、几乎无标点**，正是"一地碎片"。
这同时**证实了 §1.5 ③ 的勘误** —— 原 A/B 测在 `0~604 s`（那个区间本来还有标点）才得不出结论，
换到 `780~1384 s` 立刻显形。

**② 1D 确实修好了它。** B 臂 94.7% 有标点（**排除复读组后仍有 91.2%**），段数减半、段均字翻倍。

**③ 真正起作用的是「术语表」，不是 `-sns`。** C 臂带齐了 `-sns` 与 `--carry-initial-prompt`
但用短 prompt，只有 14.7% —— 且分桶显示它**前 4 分钟还有 88% / 75%，之后塌到 0%**，
等于在窗口内部重演了一次"越往后越忘"。所以抬断句质量的是**把术语表拼进 `--prompt`**，
另外两个开关是配套（`-sns` 压非语音 token、`--carry-initial-prompt` 让术语表不只在开头生效）。

**④ 新出现的代价：B 触发了一次复读幻觉** —— 最高频段落「那些资料要分层。」重复 **44 次**
（A 臂最高频只是口语「嗯」16 次，C 臂 0 次）。这不是顺带的好处，而是**必须由 1C 兜住的副作用**：
`TranscriptCleaner` 的复读折叠就是为这种串设计的（阶段 0 实测过单串重复 86 次）。
**结论：1C 与 1D 互补，不能只上其中一个。**

**为什么「概述」从第 1 位降到第 6 位**：验收标准是「一屏内看到结论 + 要点 + 谁做什么」，
而概述是 200~400 字的一段话 —— 它霸着最前面，就会把下面四块全推到折线以下。
它没有变得不重要，只是**不紧急**：前五块是索引，它和第七块是正文。

**其它设计决定**：

- **摘要上限 3 条**（`summaryLimit`）。3 是"一屏内"倒推的：三段小标题 + 三行摘要 ≈ 200pt。
  列全（长会 16 条）这一页就只能当纪要读了。超出的走行尾「查看全部 ›」跳纪要页。
  **只在真的藏了内容时才给按钮** —— 正好 3 条时不显示（`items.count > summaryLimit`）。
- **摘要行只占一行、不带依据**。纪要页是终稿（每条都能溯源），速览页是索引（扫完就走）。
  截断掉的那半句由 `.help` 兜底，悬停可读。
- **时间锚先定位再播**（`seek` + 播放器没在播就起播）：点一个时刻的全部意图就是"我要听这一段"。
  音频没加载出来时锚**退化成纯文字**（`onJump = nil`）—— 点了没反应比不可点更糟。
- **老会话（2A 之前）整块退化**：没有 `headline` / `overviewBullets` / `openQuestions` 就直接不渲染那几块，
  页面回到"摘要 + 导语 + 时间轨"，不是一屏空白。已用**真实老会话数据**跑过回归（见下）。

> `reloadSessions` 里那个只认「本地整理」档的循环压根不会碰它。
> 所以补了一个**两道锁**的修补循环（`needsMaterialGateRepair`）：**材料确实不够** 且 **结果里没有任何结构化发现**

> （哪怕材料少，那也是用户真正拿到过的东西）。**逐字稿任何时候都不删。**

1. **解析只认逗号类分隔符，不认空格** —— 英文术语自带空格（`Product Hunt`），用空格切会把一个词切成两个。

   "我明明加了这么多词，怎么一个都没进转写"。

   而现象是"转写结果看着正常，只是错词还是老样子"，没人能看出是这里出的问题。

`TranscriptCleaner.applyingTerminology`（**只换字，不折叠 / 不并句 / 不丢段**，段数与时间戳一律不变），
改到了才写回，没改到就一个字都不碰盘；状态文案也会说「纪要已更新，并应用了术语表」。

### 2E 已完成（2026-09-14）—— 逐字稿就地编辑 + 一键重整理 · **阶段 2 收口**

**落点**：新增 `TranscriptEditor.swift`（纯逻辑：归一化 / 判决 / 计数；**必须同步加进 `Package.swift` 白名单**）、

**它修的是哪条现场**（方案 S4）：用户看到错词（客户→课考、拜访→败网 这类同音误听）**没有任何办法就地修正**，
错词会一直传染到速览和纪要；用户唯一的出路是反复点「重新整理」，而重试并不会让词变对。

**三个设计决定**（每条都有反例）：

| 决定 | 不这么做会怎样 |
|---|---|
| **立即落盘**，不做"保存全部" | 改的是**一句**具体转写，没有第二个动作会覆盖住它；攒在内存里，关窗 / 退出就没了 —— 而用户以为自己改过了（他确实点了保存），下次打开发现白改 |
| 段级记 `manuallyEditedAt`，不只记会话级 | `applyingTerminology` 每次「重新整理纪要」都会跑。只记会话级的话，用户手改的那句会被术语表**再替换一次**：他改掉「课考」，表又把它换回去 —— **改了半天白改，且没有任何报错**（文本依然通顺、依然存得下、依然渲染得出来） |
| 正在整理时**拒绝**编辑（`isProcessing`） | 那一句正是模型这次要读的材料。放它进来会得到"模型整理的是旧文本、用户看着的是新文本"，谁也解释不清 |
| 不允许把一段改成**空** | 删掉一段等于删掉那几十秒音频在纸面上的存在，而每段背后都挂着时间戳与真实录音。要丢掉整段，得连录音一起删这场会议（沿用 2C「逐字稿任何时候都不删」） |
| 页眉那句「原汁原味保留转写」**改过之后必须换掉** | 它就是字面事实的声明，同 2C 的 `summaryModel`：有人工校正之后还留着这句，是一句看得出来的假话。改后 → 「已人工校正 N 处」（同时解释了为什么被改过的段尾不再有机器置信度） |

**判据只有一处**：`TranscriptEditor.verdict(for:against:)` 同时决定「界面那颗保存键亮不亮」
与「写不写盘」。两处各写一份的话，迟早出现"按钮亮着但点不动"（或反过来），两个方向都不报错 ——
配了一条遍历式单测（`testVerdictAndApplyNeverDisagree`）把两者拴住。

**端到端：改一句 → 真的落到盘上**。`TranscriptEditorTests` 只证明"该不该改"，
而用户冒的风险是"下次打开还是不是我写的那个版本"。为此给 `MeetingStore` 开了
`init(storage:)` —— 数据根**显式**传一个临时目录，绝不走环境变量（那条路一旦没生效，
测试会写进**真实数据根**，这在本项目已经被证明过一次）。4 条 `TranscriptEditPersistenceTests`
验的是：盘上文本 / `manuallyEditedAt` / `transcriptEditedAt` / 派生 `transcriptText` 四样一起走，
而未编辑的段一个字节不动。

**3-3：LLM 裁判。** `Scripts/llm_judge.py`，四维各自一次独立调用（不合并 ——
合并会让模型在「举证据」和「打分」之间互相迁就），打分 1~4，任一维中位数 < 3 即未过。
默认裁判 `agnes-3.0-flash`（Agnes），被评产出是 DeepSeek，**异厂**；
同厂模型必须显式 `--allow-same-vendor` 才放行。

实跑（2026-09-14，`slice1-0-15min`，`--repeat 3`）：

| 维度 | 分数 | 中位数 |
|---|---|---|
| 忠实度 | [2, 4, 4] | 4 |
| 覆盖度 | [3, 4, 4] | 4 |
| 信息密度 | [4, 4, 4] | 4 |
| 可执行性 | [2, 2, 2] | 2 |

两条结论都值得留档：

1. **单次跑不可用。** 忠实度三次跑出 `[2, 4, 4]` —— `--repeat 1` 时「达标/未达」本身是掷硬币。
   所以脚本内置 `--repeat N` 取中位，抖动如实记进 `judge/<caseId>.json` 的 `runs` 字段，
   `--check` 在 `--repeat 1` 时会主动提示。
2. **裁判独立复现了客观指标的结论。** 可执行性三次都是 2/4，理由是「除 AI 方案外其余待办
   既无责任人也无时间节点」；同一场 `actionsWithOwnerRatio` = 0.125。
   一个只读文本的裁判，独立指向了 §6 里那条 P2-2a 的触发条件 —— 这才是「两条独立路径
   指向同一结论」的证据。

裁判的提示词也按实测收紧过一次：首跑把「赵瑞梅」也列进了「无依据」清单（它自己在
note 里刚说过这个名字有依据），同一处人名写错被重复计数。现在明确要求
「同一个信息点的同一个偏差只算一处」「拿不准的标存疑，宁可少报」——
一份充满误报的清单会让人去修没坏的东西，这是本项目已经栽过 6 次的坑。

**全量实跑（5 个 case，`--repeat 1` 作参考）又抓出两个真缺陷**，都值得留档：

1. **拿不适用的维度去评「本来就不该有内容」的对象 —— 第 7 次同型口径错。**
   `too-short`（误录到在线视频的推广语）**正确的产出就是什么都不写**，
   而裁判照四维打分，可执行性给了 **1/4**，理由是"没有待办、没有责任人"。
   危害不是这一个低分，而是它会被读成"这一场质量差"，甚至诱导人去修一条没坏的路径。
   修法：把 case 的 `expect` 传给裁判，空态场**只评忠实度**（唯一有意义的问题是
   "有没有编造出不存在的会议内容"），其余维度显式记 **`n/a`（不适用）并排除出统计**。
   **三种状态必须分开：分数 / 不适用 / 跑失败** —— 不适用不等于 0，也不等于失败。
2. **裁判的列举类字段会被截断。** `slice3` 的信息密度一次跑失败，报
   「响应里找不到 JSON 对象」—— 模型列「废话句」列超长，JSON 没闭合。
   两个修法一起上：`JUDGE_MAX_TOKENS` 6k → 12k；提示词限制「最多 8 条、每条不超过 30 字」。
   另外**解析失败时要把 `finish_reason` 一起报出来** —— 否则"被截断"和"不是 JSON"
   这两种病只能靠猜。

这两条已回写进 `llm-content-quality-eval` 技能的
`references/metric-pitfalls.md`（事故 7）与 SKILL 的裁判小节。

> **结论：命中触发条件 #1 —— 阶段 4 做 `P2-2a` 双声道录音。**
> 五个触发条件里**有且只有一个命中**，所以 P2 就做这一项，不做别的，也不"顺便"做别的。

#### 逐条核对

| # | 触发条件 | 实测（5 case，2026-09-14） | 判定 |
|---|---|---|---|

第 3 条值得单独交代一句：`long-full` 的 0.305 只是**清洗后段数 / 原始段数**比目标略高一点
（266/871，段均 45.5 字），不等于"用户抱怨碎裂"。把它和"用户抱怨"混为一谈，就会去调一个
没人在抱怨的东西 —— 正是本计划反复在防的那类错。

#### 为什么是「材料缺口」而不是「抽取缺陷」（这一步不能省）

一条低指标有两种病因，治法**正好相反**：材料里没人说"谁负责" → 只能从材料侧补；
材料里明写了、模型没抽出来 → 该修抽取 prompt。**直接按"低 → 优化 prompt"动手是赌博。**

所以先量了「材料侧天花板」（`Scripts/probe_owner_gap.py`，材料侧与产出侧**同一个分母**）：

| 指标 | 值 |
|---|---|
| 逐字稿里「点名的指派」条数 ÷ 产出待办总数（**材料侧天花板**） | **22.9%**（8 ÷ 35） |
| `owner` 非空的待办 ÷ 产出待办总数（**产出侧实得**） | **17.1%**（6 ÷ 35） |
| 通过率（实得 ÷ 天花板） | **75%** |

**天花板 22.9% 本身就在 30% 的线下面。** 两条结论：
1. **再完美的抽取也到不了线。** 想靠改 prompt 达标，唯一的路是让模型**编出责任人** ——
   把"缺信息"换成"幻觉"。数字好看了，内容变假了，而且没人看得出来。**这条路不走。**
2. **通过率 75%（6/8）说明抽取链路是好的**，天花板上的 8 条它抓到了 6 条。**别动它。**

逐字稿里 1744 段只有 **14 段（0.8%）**含指派/承接语，其中还夹着"这个我不负责"式的否定句
（口径是高估的）。**材料层面本来就极少有人把活派到具体人头上** —— 这才是 16% 的真正来源。
所以这一刀只能从材料侧切：**把"我方 vs 对方"分开，让「你负责」这类指代变得可判定**。

#### 预期管理：做完 P2-2a 也别指望这条指标到 30%

材料侧天花板 22.9% 是**当前条件下**的上限。双声道能抬的是其中**靠"你"指代**的那部分
（真·可判定的跨方指派），抬不到"会议里根本没人点名"的那些待办上去。

所以 P2-2a 的验收标准**不是**"`actionsWithOwnerRatio` ≥ 30%"（写这条等于给自己埋一个
必然不达标的坑），而是：

- 逐字稿每段都带上 `speaker`（我方 / 对方），**且人工抽查 20 段标注正确**；
- 材料侧天花板**从 22.9% 抬起来**（用同一把尺子前后对比，`probe_owner_gap.py --json`）；
- 纪要与速览里出现**可判定的跨方表述**（"我方要求对方…"、"对方确认…"），
  而不是把双方的话混成"会上讨论了…"。

#### 裁判旁证（`--repeat 3`，2026-09-14）

`Scripts/quality_report.sh --judge --repeat 3` 全量跑完（4 有内容场 × 4 维 + 1 空态场 × 1 维，
各 3 次 ≈ 51 次调用，约 7 分钟）：

| 维度 | 中位数 | 各场中位 | 稳定性 | 判定 |
|---|---|---|---|---|
| 忠实度 | 2 | 2/2/2/2 | 一致（每场都未达） | 未达 |
| 覆盖度 | 4 | 4/4/4/4 | 一致（每场都达标） | 达标 |
| 信息密度 | 2.5 | 3/4/2/1 | ⚠️ **不一致 → 不能当依据** | （中位 2.5） |
| 可执行性 | **2** | 1/2/2/2 | **一致（每场都未达）** | 未达 |

`too-short`（期望空态）**单独判**：忠实度 4 —— 它没有编造出一场不存在的会，
这正是该场唯一有意义的问法。

**① 可执行性：旁证成立。** 裁判四场一致给 2/4，理由每次都是「待办缺责任人 / 缺时间节点」，
而同一套 case 的 `actionsWithOwnerRatio` 中位 16%。**两条互不依赖的路径同向、且都稳定** —— 这才算证据。
指向与上文一致：做 P2-2a。

**② 「忠实度 2/4」查证后不成立 —— 这条比上面那条更重要。** 数值上忠实度 4/4 场未达，
看起来比"没写谁负责"严重得多。按本项目规矩抽原始样本回原文核对，**指控经不起核对**：

| 裁判的指控（`long-full`，score=1 那一跑） | 回逐字稿核对 | 结论 |
|---|---|---|
| 「将'8小时超时'误记为'80'」 | 逐字稿里**既无「8小时」也无「八小时」** | **虚构引文**：它替原文编了一个版本来证明产出写错 |
| 「'12份'是无依据数据」 | 逐字稿 `[2266s]`「它从购买到下单收到,那就是12份」 | **误报**：原文明写 |
| 「'6名同事'误记为'六亿个'」 | 逐字稿原文就是「有六亿个同事在同步设计着」 | 产品**如实保留**了转写错误；裁判在判**正确性**，不是**忠实性** |

同一份产出跑四次得 `[3, 1, 2, 3]`，而**最准的那一跑（score=3）自己的结论是「未发现重大事实性幻觉」**，
只对「'80' 的含义在原文不明确、产出做了过度解读」提了一条合理的存疑。
→ **忠实度不是产品缺陷，是裁判不可靠。** 照数字去改 prompt，就是在修一个没坏的东西。

这是本项目**第 9 次**同型事故，形状是新的：前 8 次都是「指标口径 / 适用性」错，
**这一次是「裁判自己会编造依据」**。已固化成三条纪律：

- 报告里只要有负分，就**固定挂一句「负分先核对」**（`render_report`），
  写明实测过的三种坏法：误报、虚构引文、把转写听错当模型幻觉；
- 技能 `llm-content-quality-eval` 新增**事故 9**；
- `--repeat` 的产物现在同时给**「各场中位 / 稳定性 / 逐次分数」**，并且**聚合只收有内容的场** ——
  空态场那个白送的 4 分会把真实缺陷的中位抬上去（这也是本轮当场抓到的另一个口径错）。

#### 阶段 4 · P2-2a 实施计划（API 路线已探明）

**现状病根**：`MixedRecordingSession`（`WhisperPipeline.swift:120`）用 `SCRecordingOutput`
直接落一个**已经混好音**的 `.mov`，且 `channelCount = 1` —— 两路在**采集那一刻**就合并了，
"我方 vs 对方"不可能事后恢复。

**macOS 15 的 SCK 本来就把两路分开投递**：`captureMicrophone` 把麦克风音频送到**独立的
`.microphone` 类型 `SCStreamOutput` 回调**，系统声走 `.audio`（Apple 官方 `Capturing screen
content in macOS` 示例同时 add 了 `.screen` / `.audio` / `.microphone` 三个 output）。
而且**同一个 `SCStream` 会话 = 同一个时钟** —— macOS 15 之前那个"双源时钟漂移、录到 30 分钟
就对不齐"的老问题在这里不存在。

**路线**：同一个 `SCStream` 上挂两个 output → 各写一个 16 kHz 单声道 wav（`mic.wav` / `system.wav`）
→ 各跑一次 `transcribe`（`WhisperPipeline.transcribe` 本来就是按文件跑的）→ 按时间戳合并、逐段打 `speaker`。

**否决的两个备选**（记下来免得以后有人重新提）：

| 备选 | 为什么不用 |
|---|---|
| 单路混合转写 + 按时间窗能量判说话人 | 省一半转写耗时，但**耳机/外放会直接改变正确率**：外放时麦克风把对方的声音一起收进来，标签就废了。而且判错说话人是**看不见的数据损坏**（本项目最怕的一类） |
| 两路写进同一个双声道文件 | 多一层拆声道的工作，没有任何好处 |

**改动清单**：
1. `MeetingModels.swift`：`TranscriptSegment` 加 `speaker`（新增 `enum TranscriptSpeaker`）
   —— **Optional + nil 省略键**，老会话照旧能解（§6 原文已点名要"预留 `speaker` 字段"）。
2. `WhisperPipeline.swift`：录音会话产出**两路文件**（保留单路麦克风模式作为降级）。
3. **合并逻辑抽纯函数**（如 `TranscriptMerger.merge(mic:system:)`）+ 单测。
   ⚠️ 不要把它写成录音类里的私有方法 —— 那样它在 `swift test` 里根本跑不到，
   而它决定的正是**用户可见的说话人归属**。
4. `Package.swift` 白名单同步（新增 `.swift` 必加，否则编译不过）。
5. 整理 prompt：把 `speaker` 带进材料，让纪要与速览能写"谁提的/谁答应的"。

**代价与风险**（如实写）：

- **转写耗时与开销翻倍**（两路各跑一次 whisper）。缓解：某一路全程近乎静音时（对方静音、
  或只有我说话）识别出来就跳过第二次转写。
- **实现无法用 CI 覆盖**：合并逻辑可以全自动测，但"录音确实分出两路"必须有**真实音频**。
  ⚠️ **本机无法自动造出两路真实音频**，所以这一条必须在交付里写明"未实测"，
  验收动作是人工做一次 10 分钟自测（一半靠系统音频播放、一半对着麦克风说）。
- 权限文案与失败态要同步更新：原来只有"屏幕与系统音频"一种权限失败，现在多一个麦克风。

**降级阶梯（每一级都退回到"和改动前一模一样"）**

2. 某一路全程静音 → 跳过这一路的转写 → 另一路的段落照常带标签。
3. 两路都静音 → 返回空逐字稿 → 走「材料不足」那条路（**根本不调模型**）。
4. `SCStream.addStreamOutput` 抛错（比如系统不认识 `.microphone`）→ 这一路没有，其余照旧。
5. 写入中途换了格式 → **立刻停手**并记下原因，绝不把两种格式混进同一个文件。

#### 阶段 4 · 实测事故与修复（2026-09-14 上午，人工自测第一轮）

**现象**：人工自测录了两场（各两分多钟），原文页**完全没有** `[我方]` / `[对方]`。

**真因在接线，不在采集层**：`MeetingStore.startRecording()` 构造 `MixedRecordingSession` 时
只传了 `movieURL`，`localTrackURL` / `remoteTrackURL` 吃了 `URL? = nil` 的默认值 →
`start()` 里那两个 `if let` 直接跳过 → 两路**从未挂上** → 静默退回单路。

**它为什么能藏住**：这正是设计好的降级行为（"少一路就降级，录音本身照旧"）。
于是这个 bug 的表现，与"系统根本不支持 `.microphone`"**一模一样** ——
编译通过、177 条测试全绿、录音与转写完全正常，用户唯一看得见的是"没有说话人标签"。

**旁证（数据侧）**：两场会话的 `session.json` 里 `captureMode` 是 `mixed`，
但 `localAudioFileName` / `remoteAudioFileName` 都是 `None`（键被省略），
`transcriptSegments` 连 `speaker` 键都没有；会话目录里没有 `local.wav` / `remote.wav`，
`chunks/` 里只有 `chunk-0001.json`（单路命名）。

**修复**：

1. `MixedRecordingSession.init` 的两路参数从 `URL? = nil` 改成**必填** ——
   让"忘接线"变成**编译错误**，而不是一次安静的单路降级。降级本身保留，
   但它只应该发生在**运行时**（`addStreamOutput` 抛错、挂上了但样本没来），
   不该发生在"参数没传"这种编译期就能拦下的地方。
2. 落盘命名抽成 `DualTrackPaths`（单一事实来源，`capture` 与 `normalized` 两组名字
   必须不同，否则 afconvert 输入输出撞车）+ `DualTrackPathsTests` 6 条钉住。
3. 整条链路接入 `os.Logger`（`Diagnostics.swift`）：接线 → 挂载 ×2 → 收尾帧数 →
   归一化 ×2 → 转写计划 → 合并结果，共 5 类节点各一行。排查一条命令：

   ```
   log show --last 30m --predicate 'subsystem == "com.qingmeng.meetingscribe"' --info
   ```

   **少了哪一行，就是断在哪一环。**

**同时实测掉的未知**：探针（`Scripts/probe_dual_track_delivery.swift`）证明
`.microphone` / `.audio` 两个 output 都能挂上、两路都在持续投递样本。
所以"双声道能不能做"这件事**已经有答案了** —— 剩下的只是"标签标得对不对"。

**⚠️ 哪个动作本身仍然没有被实测（不要拿夹具截图冒充交互验证）**

- **外放时的串音到底长什么样**：合并规则里 0.6 那条线是**推出来的，不是标定的**。
  自测时若看到该收敛的重复段没收敛，就是这条线偏了。
- UI 侧：夹具只证明"有说话人时这一行**渲染**成什么样"；"录音真的产出这种数据"
  要等修复后的人工自测确认（第一轮为什么没通过，见上）。

**验收动作（人工 10 分钟，必须做）**

1. **装新包**（关键：`/Applications/MeetingScribe.app` 里那份可能仍是**旧包**）→ 跑 `./Scripts/install_app.sh`。
   注意脚本里的 `rm -rf` 会**被批量删除保护拦下**（本轮实测：`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`），
   被拦就手动两步：旧包 `mv` 进废纸篓 → `ditto .build/MeetingScribe.app /Applications/MeetingScribe.app`。
   装完用一句 `md5 -q` 核对两个路径是否**完全一致**（这是"装的确实是刚编译那份"的硬证据）。
   **换包后两道权限都要重新给**：点「开始录音」时应当弹出**麦克风**授权窗（这是第二轮加的，
   之前从来没请求过）→ 点「允许」；屏幕录制若也失效就一起重新允许；
2. 开一个能出声的会（或放一段视频）**外放**，自己同时对着麦克风说话 —— 一半系统声、一半自己说话；

   这四处**少了哪一行**：少了第一处 = 调用方没接线；第二处报错 = 系统不接受 `.microphone`；

   第四处写 0 帧 = 挂上了但系统没投递样本（权限已给的情况下才需要往这一步查）。

#### 阶段 4 · 实测事故与修复（第二轮，2026-09-14 上午）—— **第二个断因**

**现象**：修完接线、装了新包，第三场（30 秒）录下来——原文页**仍然没有** `[我方]` / `[对方]`。

**这次的真因是权限，不是接线**：`MixedRecordingSession.start()` 只请求了**屏幕录制**授权，
**从来没请求过麦克风授权**（`AVCaptureDevice.requestAccess(for: .audio)`）。
而 `captureMicrophone = true` 缺麦克风授权时，ScreenCaptureKit **不报错、也不给样本**：
`.microphone` 那一路全程 0 帧 → `makeResult()` 把它当成"没有这一路" → 又退回单路。

**数据侧的铁证**（这次能直接区分两个断因）：

| 观察 | 本轮结果 | 含义 |
|---|---|---|
| `remote.caf` | **在**（1.9 MB） | `.audio` 那一路挂上了、也在持续收样本 |
| `local.caf` | **不在** | `.microphone` 那一路 **0 样本**（空文件被 `AudioTrackRecorder` 删掉） |
| `local.wav` / `remote.wav` | 都不在 | 本地路缺失 → `normalizedTracks` 提前返回 → 不做标注 |
| `session.json` 的 `speaker` 键 | 没有 | 与"接线漏传"**表现完全一样** |

**关键教训**：「原文没有说话人标签」这一个现象，一天之内对应了**两个完全不同的真因**
（① 接线漏传两路；② 麦克风权限从没请求过）。两者都"编译通过 + 177 条测试全绿 + 录音与转写正常"，
**现象一字不差**。所以排查不能靠"再仔细看看代码"，只能靠**新增能区分它们的判据**
（各路的帧数 / 中间文件在不在）。这也是 `Diagnostics` 存在的全部理由。

**修复**：

1. 新增 `MicrophoneAccess`（`WhisperPipeline.swift`）：`request()` 请求授权 +
   `statusLabel` 记录**请求前**状态（「从未询问」要弹窗、「曾被拒绝」只能去系统设置改，
   两种处置完全不同）。`MicrophoneRecordingSession` 一并改用它，去掉重复实现。
2. `MixedRecordingSession.start()` 在请求屏幕授权之后**再请求麦克风**，并把
   「请求前状态 + 最终结果」写成一行日志。**授权失败不抛** ——
   拿不到麦克风只是没有说话人标注，录音本身照旧（降级阶梯原则不变）。
3. `normalizedTracks` 提前返回时**清掉没用上的中间文件**（`discardCaptureFiles`）——
   第二轮实测在会话目录里留下过一个 1.9 MB 的 `remote.caf`，它长得像"其实录到了两路"的证据。

**⚠️ 探针的适用边界（修正上一轮的乐观结论）**：`probe_dual_track_delivery.swift` 以 **CLI 进程**
运行并拿到了麦克风样本，只证明「**系统会把两路分开投递**」，
**不证明「本 App 有麦克风授权」** —— TCC 按进程 / 签名记账。探针能打掉的是"系统能力"这个未知，
不是"本 App 有没有资格"。正确的排查顺序：**① 系统能力（探针） → ② 权限（App 内显式请求 + 日志） → ③ 接线（参数必填）**。

#### 阶段 4 · 实测事故与修复（第三轮，2026-09-14 上午）—— **第三个断因 + 一个转写坏字节**

**现象**：用户再录一场后仍然没有标签，并补充一个关键动作线索：点「结束并转写」后会弹出需要输入电脑密码的授权（钥匙串访问），同意后很快跳到「速览」页并直接出现原文结果。

**第三个真因不是权限，而是样本格式被我们自己误杀**：强化探针直接复用 `AudioTrackRecorder` 的落盘路径，结果发现 `.microphone` 路的真实格式是 **48 kHz / 1 声道 / Float32 / 交错**。这是合法线性 PCM，但 `AVAudioFormat.isStandard` 返回 `false`。旧代码把「不是 standard」等同于「不可落盘」，于是麦克风那一路**明明来了样本，却被我们全部拒掉**；`local.caf` 仍是 0 字节并被 `finish()` 删除，表现又和「没权限 / 没样本」一模一样。

**修复**：`AudioTrackRecorder.format(of:)` 不再要求 `format.isStandard`，只要求「线性 PCM + 采样率 / 声道数 / 每帧字节数合理」，源格式原样落 `.caf`，后续仍由统一的 `afconvert` 归一化成 whisper 使用的 wav。日志摘要补上首个样本格式，避免以后「0 帧」同时代表权限、系统投递、格式拒绝三种病因。新增 `AudioTrackRecorderTests.testInterleavedFloat32SamplesAreAccepted` 钉住这次事故格式。

**同时修掉一个独立失败点**：10:54 那场 `chunk-0001.json` 内部有非法 UTF-8 字节（实测 `0xFC`），`JSONDecoder` 因单个坏字节报「格式不正确」导致整场失败。新增 `WhisperRawTranscript.decodeWhisperJSON(_:)`：正常路径严格 decode；只有在数据本身不是合法 UTF-8 时，才用 U+FFFD 替换坏字节后再 decode。合法 UTF-8 但 JSON 结构错误仍然抛出，不把坏 JSON 当好结果。新增 `WhisperJSONDecodingTests` 3 条钉住。

**验证**：定向测试 `AudioTrackRecorderTests` 6 通过、`WhisperJSONDecodingTests` 3 通过；全量 Swift 测试 **181 通过 / 1 skipped**。

- **双声道会话与老会话的正文左边界不同**。选择「有条件显示标签」而不是「永远留一条 32pt 空槽」，
  是为了**不动老会话的渲染**（浅色档是已验基线）。同一场会议内部的行是齐的（实测偏差 0）。
- 标签与时间戳、置信度**同档 token**（`muted` 11pt）→ 浅色下对比度低于 AA，
  **并入待办 ①** 一起修，不在这里单独调色（单独调会让这一行出现第三种灰）。
- 代价：转写耗时约为单路的 2 倍（全程静音的一路会跳过）；归一化后**删掉**中间 `.caf`
  （两路合计约 460 MB/小时），只保留 `local.wav` / `remote.wav`（约 115 MB/小时）。

**打包脚本的坑（本轮才暴露，独立于 P2-2a）**

`Scripts/package_app.sh` 里两条路径都是坏的、而且**只在打包时才炸**（`swift test` 全绿）：

1. 它的 `swift build` **没带 `--disable-sandbox`** —— 而本项目构建**必须**加它。于是这台机器上
   每次打包都会掉进 swiftc 兜底分支（"SwiftPM 构建不可用"）。
2. 兜底分支的源文件清单是**一串写死的文件名**，与 `Package.swift` 的 sources 白名单**早就漂移了**：
   2D 加进来的 `Glossary.swift` 从来不在里面。谁新增一个 `.swift`（包括本轮的两个），
   打包就会以 `cannot find type 'Glossary' in scope` 这种**和真正原因完全无关**的报错失败。

修法：① 两条 `swift build` 都补上 `--disable-sandbox`；② 清单改为从仓库根目录现取
（排除 `Package.swift` 自己，它是 manifest，带进 `-parse-as-library` 会撞车）。
改完核对过：根目录 18 个 `.swift` == 白名单 18 项，两个集合**逐文件相等**。

> **教训**：`Package.swift` 的白名单不是唯一一份源文件清单 —— 凡是"手写的第二份清单"，
> 都会在某个时间点静默漂移，而漂移的代价**只出现在最不常跑的那条路上**（打包 / 发布）。
