## 阶段 1：补两个"说不清"的状态（优先级最高）

### 1-1 模型发现状态机

**触发状态**：用户在设置里填了 Key → 点获取模型 → 失败或服务商不返回列表。

**查实的现状（本轮读码）**：`summaryTestStatus` 是**一个 `String` 字段**，被 **9 种语义**复用：

| # | 赋值 | 位置 |
|---|---|---|
| 1 | `"正在连接服务商…"` | `MeetingStore.swift:505` |
| 2 | `"已获取 N 个模型，请选择一个"` | `:534` |
| 3 | `"连接正常 · 已获取 N 个模型"` | `:535` |
| 4 | `"连接正常 · 服务商未提供模型列表，请手动填写模型 ID"` | `:541` |
| 5 | `"正在测试当前模型…"` | `:543` |
| 6 | `"连接正常 · 当前模型可用"` | `:556` |
| 7 | `error.localizedDescription`（**原样透出**） | `:569` |
| 8 | `"API Key 保存失败，请重试后再获取模型"` | `:492` |
| 9 | `"已选择 X · 会后整理将使用它"` | `:581` |

**这正是项目已经学过的教训在设置页重犯**。§24.8 原文："语义不同的状态必须新开字段：把'我们主动没调模型'塞进 `summaryError` 会连锁错三处"。`summaryTestStatus` 是同一个反模式，只是发生在设置页。

**两个具体缺陷**：
1. **失败态不可区分**。网络不通 / Key 无效 / 端点格式错 / 服务商不提供 `/models` 四类原因全部塌进第 7 行，且直接显示 `localizedDescription`（多为英文技术串）。用户拿到的是"操作失败"之外的原始错误，不知道该改什么。
2. **主窗口不显示模型不可用**。状态只活在设置面板里；主窗口的"重新整理"看起来永远可用（`canRegenerateSummaryNow` 只判内存 Key，不判模型可达性）。

**改法**：
- 拆成 enum：`idle / connecting / loaded(count) / noList / testing / available / failed(reason) / keySaveFailed / selected(name)`，每个 case 自带渲染，替代 `summaryTestStatus` 字符串。
- `failed(reason)` 的 reason 分四类，各自给"下一步做什么"；不再透出 `localizedDescription`（改为记日志）。
- 主窗口加**一条常驻状态**：整理模型当前是否可用。不可用时"重新整理"按钮说明原因而不是静默变灰。

**验证判据**：9 种语义各自有独立 case 与独立文案；`grep -c "summaryTestStatus ="` 归零或仅剩日志用途；新 enum 的每个 case 有单测。

**可在离机时完成** ✅

### 1-2 缺系统音频录制权限

**触发状态**：首次录音，或系统更新后权限被重置。

**查实的现状（本轮读码）**：
- `WhisperPipeline.start()`（`:254`）先 `requestScreenAccess()`，失败则抛文案（`:257`）："未获得屏幕与系统音频录制权限。如果刚刚允许，请完全退出并重新打开 MeetingScribe 后再试。"
- 麦克风是**另一道门**，在 `:267` 单独请求，失败**不抛**，只写日志（`:273-279`）。
- 结果：**两道权限，用户只看到一句合并的文案**；麦克风失败完全不出现在界面上。

**改法**：
- **前置 preflight**：空闲态用 `CGPreflightScreenCaptureAccess()` 与麦克风 `authorizationStatus` 分别判定，在**开始录音之前**就把状态显示出来——而不是等用户点了录音再抛错。
- **分权限显示**：系统音频 / 麦克风各一行，各自的开关状态与"去授权"入口。麦克风缺失要说清后果是"本次不会有说话人标注，录音照常"，而不是沉默。
- **把 macOS 的限制说成限制**：屏幕录制权限变更后必须完全退出重开，这是系统的行为，不是 App 的 bug——文案要把它讲成一句可操作的说明。

**验证判据**：四个组合（两权限各有/各无）都有对应的界面状态；"开始录音"在缺权限时给的是**可执行的下一步**，不是一句错误。

**可在离机时完成** ✅（用夹具渲染四种组合）

## 阶段 2：清除污染源——死代码 714 行

**为什么排这么前**：它不是"不好看"，它是**此后每一次改动的隐患**。

**查实的现状（本轮读码）**：`ContentView.swift` 全文 **714 行**，是一整套与活代码**平行的第二套 UI 词汇表**：

| 死代码（ContentView.swift） | 活代码对应 |
|---|---|
| `LegacyContentView`（:39） | `ContentView`（在 `WorkbenchView.swift`） |
| `SettingsView`（:569） | 活的设置面板 |
| `SessionRowView`（:244） | `WorkbenchSessionRowView` |
| `SessionDetailView` / `SessionDetailSection` | `WorkbenchResultDocument` 系列 |
| `OverviewSection` / `DecisionSection` / `ActionSection` | 速览页 / 纪要页各分组 |
| `InsightRow` / `TimelineRow` / `TranscriptRow` / `ActionRow` | 各 `Workbench*Row` |
| `StatusBadge` / `MetaBadge` / `ConfidenceBadge` / `PriorityBadge` | 状态点 / 元信息行 |

**近同名、同 module、共享 `AppTheme` 与同一批模型**。改 token、改模型字段时改错文件**不会报错**。这是一颗已经埋好的雷。

**改法**：
1. 先做**引用清点**：对 16 个类型逐个 `grep -rn` 全仓引用，确认零引用（有引用的先摘出来）。
2. 确认后整体删除，同步 `Package.swift` 白名单。
3. **跑一次打包**（§24.1 的教训：手写的第二份清单只在最不常跑的路上爆炸）。

**验证判据**：`grep -rn` 对 16 个类型零引用；184 测试全绿；打包成功且 `md5` 一致。

**可在离机时完成** ✅

## 阶段 3：可用性两项（不是审美）

### 3-1 11pt 元信息对比度

**查实的现状（本轮按 token 复算，待像素复核）**：

| token | 浅色值 | 对白底理论对比度 | 判定（AA 文字 4.5:1） |
|---|---|---|---|
| `warning` | `(0.945, 0.596, 0.149)` | ≈ **2.3:1** | ✗ 最差 |
| `success` | `(0.132, 0.635, 0.341)` | ≈ **3.3:1**（像素实测 2.75:1） | ✗ |
| `danger` | `(0.854, 0.204, 0.239)` | ≈ **4.6:1** | ✓ **达标** |

> ⚠️ **口径修正**：既有记忆写的是"语义色不是正文色（浅色 2.75:1）"，容易读成"三个语义色一律不能用"。
> 按 token 复算，`danger` 是**达标**的。**这是"指标口径错会带人修没坏的东西"的典型形态** ——
> 动手前必须对每一处**逐个像素实测**，不能按色号一刀切。

**涉及站点（`WorkbenchView.swift`）**：`:1840`（danger）、`:1875`（warning）、`:3301`（success）、`:3623`（warning）；另有 42 处 `.caption` 需按是否承载语义抽样。

**改法**（沿用既有结论，不走弯路）：
- **语义给图标、可读性给文字**：`Label` 的图标与文字同色，要拆成 `HStack`，图标留语义色、文字用 `muted`（4.96:1）或 `ink`（15:1）。
- **不用 `opacity` 弱化**（它是乘法，会把贴线的色压到线下）。
- 先做像素实测把"哪些真的不达标"钉死，再改——否则会修到没坏的地方。

**验证判据**：逐站点像素取样（浅色取**最暗**、且**避开图标列**），报告里写明取样区域；改前改后同口径对照。

**需你在电脑前？** 部分——像素取样可离机做，但最终"看着是否失衡"要你确认。
