### 现象

主窗口顶部在视觉上出现两条横向栏，看起来像「双层导航栏」：

| 层级 | 来源 | 内容 |
|---|---|---|
| 上层 | macOS 统一标题栏（原生） | 左上角交通灯（关闭/最小化/缩放）、侧边栏开关、窗口标题 `MeetingScribe` |
| 下层（第一行） | 应用自绘 `WorkbenchGlobalActionBar` | 「会议工作台」标题、状态行、`导入音频` / `开始录音` / `设置` |
| 下层（第二行） | `WorkbenchResultTabBar` | `原文` / `速览` / `纪要`（仅在有已完成的会议时出现） |

`ContentView.swift` 用的是 `NavigationSplitView`，SwiftUI 会把标题栏区域和自绘首行叠在一起；再叠加侧边栏里另有一个大号 `MeetingScribe` 品牌标题，于是出现「同屏三处标题、两到三条栏」的观感。

### 正确的改法（推荐）

1. **不再自绘顶部操作栏。** 删除 `WorkbenchView.swift` 里的 `WorkbenchGlobalActionBar`，把 `导入音频` / `开始录音` / `设置` 用 `.toolbar { ToolbarItem(placement: .primaryAction) { ... } }` 注册到原生标题栏，与侧边栏开关同一行。
2. **主窗口标题只保留一处。** 侧边栏保留品牌名，原生标题栏标题改为当前会议名（无选中时留空或写「会议」），避免 `MeetingScribe` 重复出现三次。
3. **结果页 Tab 不占独立空白栏。** `WorkbenchResultTabBar` 只在 `session.status == .ready` 时渲染（当前逻辑已如此），空状态时不要保留占位高度；并在内容区左侧对齐，而不是顶着分隔线单独成条。
4. **侧边栏顶部留白不要手写。** `WorkbenchSidebarView` 里 `Color.clear.frame(height: 36)` 是为避开交通灯的临时手段；改用原生 `NavigationSplitView` + `.toolbar` 后这一行应当删掉。
5. 改完必须**截图 + AX 树双验证**：确认交通灯区域无重叠、顶部只剩一行、空状态与有会议状态都不出现空白条。

### 验收标准

- 顶部横向栏数量 = 1（原生标题栏），其中包含侧边栏开关与全局操作按钮。
- `MeetingScribe` 在整屏出现次数 ≤ 1（侧边栏品牌名）。
- 空状态与已完成会议状态下，内容区起点一致，无空白导航条。

## 二、屏幕录制权限（已确认为环境问题，代码侧仍需改进）

### 已发生的事实

- 应用为**自签名**（`PM Studio Signing`，非 Apple Developer ID），无 TeamIdentifier。
- 授权状态在系统设置 → 隐私与安全性 → 录屏与系统录音里表现为 `MeetingScribe` 开关，**必须由用户手动打开并用触控 ID / 密码确认**，代码无法代替。
- 本轮排查中多次执行 `tccutil reset ScreenCapture com.qingmeng.meetingscribe`，导致 TCC 记录被清空、开关被复位，是「已授权却仍报未授权」的直接原因。
- **2026-09-11 17:17 实机验证已通过**：用户重新授权并**完全退出重启应用**后，点击【开始录音】→ 录制 → 【结束并转写】全流程成功，产物 `~/Library/Application Support/MeetingScribe/2026-09-11_171739_7230D26C/source.mov`（7.8 MB），`session.json` 状态 `ready`。

### 根因

1. `MixedRecordingSession.start()` 把 `CGPreflightScreenCaptureAccess()` 当作硬门禁：
   ```swift
   if CGPreflightScreenCaptureAccess() { return true }
   return CGRequestScreenCaptureAccess()
   ```
   该 API 在同一进程内会返回**过期结果**，且**不会**把应用加入系统设置列表 —— 一旦它返回 `false`，应用就直接抛错，永远走不到真正的捕获调用。
2. 权限归属代码签名身份：重新签名会改变 cdhash；未受信任的自签名证书 + 频繁重装 = 权限反复失效。

### 正确的改法

1. **去掉 preflight 硬门禁**，直接尝试 `SCShareableContent.excludingDesktopWindows(_:onScreenWindowsOnly:)`：
   - 成功 → 正常开始录制；
   - 抛错且错误域指示 TCC 拒绝 → 再提示用户去系统设置授权，并给出一键跳转链接。
   这样既避免 stale 返回值误杀，也能触发系统把应用登记进权限列表。
2. **错误文案要分情况**，不要一律写「完全退出并重新打开」：
   - 从未授权 → 「请到 系统设置 → 隐私与安全性 → 录屏与系统录音 打开 MeetingScribe 开关」；
   - 刚授权但本次进程内未生效 → 「已授权，请完全退出 MeetingScribe 后重新打开」。
   建议在错误弹窗里直接放一个「打开系统设置」按钮。
3. **开发期纪律**：
   - 不要用 `tccutil reset` 来「清干净」——会把用户已授予的权限一起清掉；
   - 重装后必须 `pkill -x MeetingScribe` 再打开，避免新旧二进制并存；
   - 构建脚本已固定使用 `PM Studio Signing`（`Scripts/package_app.sh` 的 `SIGNING_IDENTITY`），不要再退回 `-`（ad-hoc）。
4. **正式分发前的必做项**：申请 Apple Developer ID → `codesign --options runtime` → `notarytool` 公证。否则每个用户都要像这次一样手动加权限，且升级后极易失效。

## 三、会后整理模型发现的状态机（部分修复，仍有残留）

### 已修复

- `SummaryModelDiscovery.selectionCandidate(current:pending:)`：当前已选/手动填写的模型优先于 `pendingSummaryModelSelection`，不再让旧候选覆盖新输入（含单测）。
- `selectSummaryModel(_:)` 与新增的 `updateManualSummaryModel(_:)` 都会先 `cancelSummaryModelDiscovery()`，并清空 `pendingSummaryModelSelection`。
- 模型下拉在 `isLoadingSummaryModels` 期间禁用。
- `summaryAPIKeyInputDidChange()` 会失效已发现的模型列表（换 Key 后不会继续展示旧 Key 下的模型）。
- 发现结果受 `summaryModelDiscoveryID` + provider + endpoint + 输入 Key + 钥匙串 Key 五重校验，过期回调不会写状态。

### 仍存在的风险

1. **发现请求进行中不校验 `modelName` 是否被改动。** 若用户在加载过程中通过其他路径改变了模型选择，回调仍可能写回请求发起时的 `selectionCandidate`。建议把「模型选择版本号」并入 `isCurrentSummaryModelDiscovery` 的校验，或改为可取消的 `Task` + generation token。
2. **`invalidateSummaryModels()` 会清空并持久化 `modelName`。** 用户编辑服务地址后，即使新返回的列表里仍包含原来的模型，也无法自动保留。建议：把原模型作为候选保留，只在返回列表确实不含它时才清空。
3. **缺少状态机单测。** 目前 `Tests/MeetingScribeTests/SummaryModelDiscoveryTests.swift` 只覆盖解析、端点归一化、选择策略；没有覆盖「发现过程中改 provider / endpoint / Key / 模型」的竞态。建议引入可注入的发现客户端，补 4~6 条用例。

## 六、界面细节审计（2026-09-11 第二轮，已修）

> 触发方式：用户指出「按钮 / 图标 / 底部播放区域的功能间距」有问题，以「倍速控件分开两地」为例，并要求去掉底部的「录音」文字。
> 本轮的检查按 Hallmark 的 `audit` 口径过了一遍界面层（Tell / Where / Severity）。
> 注意：Hallmark 的 58 条 slop gate 面向 Web（320/375/414/768 响应式、CSS token、伪 chrome 等），
> 本项目是原生 macOS App，只适用其中「视觉 / 状态 / 排版 / 无障碍」那一部分，响应式与 CSS 相关条款不适用。

### 已修

| 问题 | 位置 | 处理 |
|---|---|---|
| **倍速控件被撕成两半**（critical）：`Menu` 未固定尺寸会吃掉横栏的全部剩余宽度，「1×」留在最左、系统下拉箭头被推到最右，实测两者相距约 680pt，并把整行挤出右侧内边距 | `WorkbenchAudioPlayerBar.rateMenu` | ① `Menu` 加 `.fixedSize()`；② `.borderlessButton` 会丢掉 label 自带的 background / overlay，胶囊底改画在 `Menu` 外层；③ 箭头改成 `Menu` 的兄弟视图并配 `.menuIndicator(.hidden)`，保证永远贴在数值右侧 |
| 底部「录音」文案没有信息量 | 同上 | 删除；只在无音频时保留「暂无可播放音频」 |
| 传输键间距 18pt 过大，三个按钮散成三块 | 同上 | 改用 `.space2`(8pt) 抱成一组 |
| 会议头贴面板左边 32pt，而 Tab 与正文是居中的 920 列，宽窗口下左边界差约 50pt | `WorkbenchSessionHeader` | 会议头也放进 `contentColumn`(920) + `contentInset`(32) 的居中列 |
| Tab 文字被居中在固定 48pt 框里，整条右移 8.5pt（实测「原文」落在 370.5pt，大标题落在 362pt） | `WorkbenchResultTabBar` | 改成下划线跟随文字宽度，并用垂直 padding 撑点击区 |
| 无底色小标签之间只有 8pt，下一项的图标贴到上一项的文字上 | `WorkbenchSessionHeader` 元信息行 | 间距提到 `.space3`(12pt) |
| 自定义 `ButtonStyle` 完全不响应 `.disabled()`，不可用状态看不出来 | `Workbench*ButtonStyle` | 新增 `WorkbenchDisabledDim`，统一按 `\.isEnabled` 把透明度降到 0.35 |

| 后退 / 前进按钮只有 `.help()`，缺无障碍标签 | 同上 | 补 `.accessibilityLabel` |
