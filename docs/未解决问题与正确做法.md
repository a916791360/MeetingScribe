### 现象

主窗口顶部在视觉上出现两条横向栏，看起来像「双层导航栏」：

| 层级 | 来源 | 内容 |
|---|---|---|
| 上层 | macOS 统一标题栏（原生） | 左上角交通灯（关闭/最小化/缩放）、侧边栏开关、窗口标题 `MeetingScribe` |
| 下层（第一行） | 应用自绘 `WorkbenchGlobalActionBar` | 「会议工作台」标题、状态行、`导入音频` / `开始录音` / `设置` |
| 下层（第二行） | `WorkbenchResultTabBar` | `原文` / `速览` / `纪要`（仅在有已完成的会议时出现） |

`ContentView.swift` 用的是 `NavigationSplitView`，SwiftUI 会把标题栏区域和自绘首行叠在一起；再叠加侧边栏里另有一个大号 `MeetingScribe` 品牌标题，于是出现「同屏三处标题、两到三条栏」的观感。

### 正确的改法（推荐）

1. **不再自绘顶部操作栏。** 删除 `WorkbenchView.swift` 里的 `WorkbenchGlobalActionBar`，把 `导入音频` / `开始录音` / `设置` 用 `.toolbar { ToolbarItem(placement: .primaryAction) { ... } }` 注册到原生标题栏，与侧边栏开关同一行。
2. **主窗口标题只保留一处。** 侧边栏保留品牌名，原生标题栏标题改为当前会议名（无选中时留空或写「会议」），避免 `MeetingScribe` 重复出现三次。
3. **结果页 Tab 不占独立空白栏。** `WorkbenchResultTabBar` 只在 `session.status == .ready` 时渲染（当前逻辑已如此），空状态时不要保留占位高度；并在内容区左侧对齐，而不是顶着分隔线单独成条。
4. **侧边栏顶部留白不要手写。** `WorkbenchSidebarView` 里 `Color.clear.frame(height: 36)` 是为避开交通灯的临时手段；改用原生 `NavigationSplitView` + `.toolbar` 后这一行应当删掉。
5. 改完必须**截图 + AX 树双验证**：确认交通灯区域无重叠、顶部只剩一行、空状态与有会议状态都不出现空白条。

### 验收标准

- 顶部横向栏数量 = 1（原生标题栏），其中包含侧边栏开关与全局操作按钮。
- `MeetingScribe` 在整屏出现次数 ≤ 1（侧边栏品牌名）。
- 空状态与已完成会议状态下，内容区起点一致，无空白导航条。

## 二、屏幕录制权限（已确认为环境问题，代码侧仍需改进）

### 已发生的事实

- 应用为**自签名**（`PM Studio Signing`，非 Apple Developer ID），无 TeamIdentifier。
- 授权状态在系统设置 → 隐私与安全性 → 录屏与系统录音里表现为 `MeetingScribe` 开关，**必须由用户手动打开并用触控 ID / 密码确认**，代码无法代替。
- 本轮排查中多次执行 `tccutil reset ScreenCapture com.qingmeng.meetingscribe`，导致 TCC 记录被清空、开关被复位，是「已授权却仍报未授权」的直接原因。
- **2026-09-11 17:17 实机验证已通过**：用户重新授权并**完全退出重启应用**后，点击【开始录音】→ 录制 → 【结束并转写】全流程成功，产物 `~/Library/Application Support/MeetingScribe/2026-09-11_171739_7230D26C/source.mov`（7.8 MB），`session.json` 状态 `ready`。

### 根因

1. `MixedRecordingSession.start()` 把 `CGPreflightScreenCaptureAccess()` 当作硬门禁：
   ```swift
   if CGPreflightScreenCaptureAccess() { return true }
   return CGRequestScreenCaptureAccess()
   ```
   该 API 在同一进程内会返回**过期结果**，且**不会**把应用加入系统设置列表 —— 一旦它返回 `false`，应用就直接抛错，永远走不到真正的捕获调用。
2. 权限归属代码签名身份：重新签名会改变 cdhash；未受信任的自签名证书 + 频繁重装 = 权限反复失效。

### 正确的改法

1. **去掉 preflight 硬门禁**，直接尝试 `SCShareableContent.excludingDesktopWindows(_:onScreenWindowsOnly:)`：
   - 成功 → 正常开始录制；
   - 抛错且错误域指示 TCC 拒绝 → 再提示用户去系统设置授权，并给出一键跳转链接。
   这样既避免 stale 返回值误杀，也能触发系统把应用登记进权限列表。
2. **错误文案要分情况**，不要一律写「完全退出并重新打开」：
   - 从未授权 → 「请到 系统设置 → 隐私与安全性 → 录屏与系统录音 打开 MeetingScribe 开关」；
   - 刚授权但本次进程内未生效 → 「已授权，请完全退出 MeetingScribe 后重新打开」。
   建议在错误弹窗里直接放一个「打开系统设置」按钮。
3. **开发期纪律**：
   - 不要用 `tccutil reset` 来「清干净」——会把用户已授予的权限一起清掉；
   - 重装后必须 `pkill -x MeetingScribe` 再打开，避免新旧二进制并存；
   - 构建脚本已固定使用 `PM Studio Signing`（`Scripts/package_app.sh` 的 `SIGNING_IDENTITY`），不要再退回 `-`（ad-hoc）。
4. **正式分发前的必做项**：申请 Apple Developer ID → `codesign --options runtime` → `notarytool` 公证。否则每个用户都要像这次一样手动加权限，且升级后极易失效。

## 三、会后整理模型发现的状态机（部分修复，仍有残留）

### 已修复

- `SummaryModelDiscovery.selectionCandidate(current:pending:)`：当前已选/手动填写的模型优先于 `pendingSummaryModelSelection`，不再让旧候选覆盖新输入（含单测）。
- `selectSummaryModel(_:)` 与新增的 `updateManualSummaryModel(_:)` 都会先 `cancelSummaryModelDiscovery()`，并清空 `pendingSummaryModelSelection`。
- 模型下拉在 `isLoadingSummaryModels` 期间禁用。
- `summaryAPIKeyInputDidChange()` 会失效已发现的模型列表（换 Key 后不会继续展示旧 Key 下的模型）。
- 发现结果受 `summaryModelDiscoveryID` + provider + endpoint + 输入 Key + 钥匙串 Key 五重校验，过期回调不会写状态。

### 仍存在的风险

1. **发现请求进行中不校验 `modelName` 是否被改动。** 若用户在加载过程中通过其他路径改变了模型选择，回调仍可能写回请求发起时的 `selectionCandidate`。建议把「模型选择版本号」并入 `isCurrentSummaryModelDiscovery` 的校验，或改为可取消的 `Task` + generation token。
2. **`invalidateSummaryModels()` 会清空并持久化 `modelName`。** 用户编辑服务地址后，即使新返回的列表里仍包含原来的模型，也无法自动保留。建议：把原模型作为候选保留，只在返回列表确实不含它时才清空。
3. **缺少状态机单测。** 目前 `Tests/MeetingScribeTests/SummaryModelDiscoveryTests.swift` 只覆盖解析、端点归一化、选择策略；没有覆盖「发现过程中改 provider / endpoint / Key / 模型」的竞态。建议引入可注入的发现客户端，补 4~6 条用例。

## 七、标题去重 / 工具栏质感 / 倍速胶囊（2026-09-11 第三轮，已修）

| 问题 | 实测根因 | 处理 |
|---|---|---|

### 本轮踩到的工具坑（值得记住）

对**同一个文件**在**同一条消息里发两次编辑**时，只有一次会真正落盘，另一次会被静默丢弃（报告仍显示成功）。本轮因此丢过三次改动：`WorkbenchStripIconButtonStyle` 的定义、`navigationSubtitle` 的替换、`AppTheme` 的 Hallmark stamp。表现是「编译报 cannot find in scope」或「改完截图没变化」。**结论：同一文件的多处改动必须串行，一次一条，改完立刻 grep 复核落地。**

**本轮起改用一次性补丁脚本**（`/tmp/patch5.py` 的模式）：把同一文件的 N 处改动写成 `(old, new)` 对，逐条断言 `text.count(old) == 1` 才替换，任一不命中就整体中止、不写盘。15 处一次过，且失败会明确报出是哪一条、片段长什么样。这比"串行手改 + 事后 grep"更省往返，也不会静默丢改动。

## 十二、转写卡片去重复 + 修「进度条后面的时间不动」（2026-09-11 第六轮，已修）

用户两条反馈（附两张实拍截图）：

1. 「转写的时候，信息展示的很重复」——卡片右上角一个「已用时 00:33」，进度条右侧又来一个「已用时 00:01」；

2. 「进度条后面的时间其实是不动的」——那个「已用时 00:01」全程停在原地，让人以为卡死。

### 根因

- **两个「已用时」其实是同一个值，但只有一个在走。** 卡片右上角那个包在 `TimelineView(.periodic, by: 1)` 里，
  每秒重算；进度框里那个写的是 `elapsedText(now: Date())`，**只在 body 求值那一刻取一次快照** ——
  而 body 只在 `session` 变化（进度推进）时才重算，所以它**只在换段时跳一下**，中途一直停着。
  截图 2 里右上角 01:55、框内 01:04，差的 51 秒就是这么来的。
- **段号三处重复**：副标题 `statusText`（「正在转写第 1/2 段 · 0%」）、卡片 `stageText`（「正在转写第 1/2 段」）、
  进度框 `progressLabel`（「0% · 第 1/2 段」）。
- **副标题末尾还有冗余状态词**：`metaLine` 拼了 `status.title`（「转写中」），而副标题前面已经顶着 `statusText` 的「正在转写…」。

### 改法

| 位置 | 改动 |
|---|---|
| `WorkbenchProcessingState.progressBox` | 删掉框内那个**冻结**的「已用时」；进度条与百分比并排一行 |
| `WorkbenchProcessingState.percentText` | 取代原 `progressLabel`，只输出百分比 —— **段号归 `stageText`，不在这里重复** |
| `MeetingSession.metaLine(includingStatus:)` | 新增开关；进行中传 `false`，副标题不再重复状态词 |

改后卡片（同一状态实拍）：

```

正在转写第 2/2 段
┌────────────────────────────────────────────────────────┐
```

## 十六、标题栏按钮统一 + 会中界面重做（2026-09-12，v0.5.0）

用户三点反馈：①右上角按钮「没质感了」；②速览/纪要「依然没有结果」；③录音/转写时

### 16.1 主按钮丢色（根因）

`.buttonStyle(.borderedProminent)` + `.tint()` **只在窗口是最前面那个时才上色**。
用户切去别的应用再回来，主操作被系统抹成灰描边。实测那一版标题栏的品牌蓝像素是 **0**。

改法：三个动作**共用一套自绘底盘** `WorkbenchToolbarButtonStyle`（实底、无描边、胶囊、
`controlSize` 统一 34pt）。主次只由**填充色**一档表达（纸白 → 品牌蓝/危险红），
不再混用「有底 / 空心描边」两种语言。方形图标钮也收成正圆，与两颗胶囊同族。

> 教训：**同一排控件不要混用「实心」和「空心描边」**。空心框挂在灰底上读起来像占位符。
> 而且要恒定着色的实底，必须自绘——系统 prominent 的着色跟着窗口活跃状态走。

### 16.2 速览 / 纪要出不来（根因）

`summaryError` 是 `NSURLErrorNetworkConnectionLost`（「网络连接已中断」）。
非流式请求在服务端生成完之前本机收不到任何字节，这条**长时间静默**的连接会被
系统代理 / 本地代理 / 服务商网关按空闲超时掐掉。

改法：`SummaryEngine.requestText` 改成 **SSE 流式**（token 持续吐出，连接始终有流量）
+ **重试 2 次**（1.2s 起步退避；4xx 除 429 外不重试），流式全军覆没再退回非流式一次。
同时把真实错误显示出来——原来 `WorkbenchSummaryFallbackNotice(message:)` 的 `message`

参考通义听悟「实时记录」与钉钉 AI 听记会中界面，两者都把**实时逐字稿**当主体。

## 十七、速览/纪要一直没结果：推理模型把 token 预算烧在思考链上（v0.5.1）

### 17.1 症状与误判

做完 §十六 的流式改造后，界面终于肯把错误说出来了，但显示的是

> 总结模型没有返回内容。

看上去像「服务商没回东西」。**实际不是。**

### 17.2 真相：接口 200，正文却是空的

用户当前配置：`https://xtapi.site/v1` + `deepseek-v4.1-flash`（provider=`custom`）。

抓真实回包（1.6 万字材料，`max_tokens: 1800`，`stream: true`）：

```
finish_reason: "length"
completion_tokens: 1800      ← 顶到上限
reasoning_tokens:  1800      ← 全花在思考链上
text_tokens:          0      ← 正文一个字都没有
content 片段数:        0
```

`deepseek-v4.1-flash` 是**推理模型**，回包里 `reasoning` 与 `content` 是两个独立字段，
思考链不计入正文。面对长材料时它先产出一大段推理，**token 预算在写正文之前就用光了**，
于是 `finish_reason=length`、`content` 为空 —— 但 HTTP 状态码是 200。

### 17.3 关键否证：关思考的开关在这家服务商全部无效

挨个试过、全部**被忽略**：

| 尝试 | 结果 |
| --- | --- |
| `reasoning_effort: "none"` / `"minimal"` | ❌ 照样推理 |
| `enable_thinking: false` | ❌ 照样推理 |
| `thinking: {type: "disabled"}` | ❌ 照样推理 |
| `chat_template_kwargs: {enable_thinking: false}` | ❌ 照样推理 |
| `reasoning: {enabled: false}` | ❌ 照样推理 |

短提示词下这些开关看不出问题（本来就不会超预算），**只有在长材料上才暴露**。
（`/v1/models` 显示该服务商只有 `deepseek-v4.1-flash` 与 `deepseek-v4-flash` 两个模型。）

### 17.4 唯一可靠的办法：把预算给足

实测同一段材料：

| `max_tokens` | 推理 tokens | 结果 |
| --- | --- | --- |
| 1 800（旧值） | 1800 | ❌ 正文为空 |
| 6 000（旧值，综合分析） | 5569 | ❌ 正文为空（贴着上限） |
| 8 000 | 3228 | ✅ 正常 |
| 16 000 | 5569 | ✅ 正常，完整 JSON |

**旧代码两条路径的预算（1800 / 6000）都低于推理链实际开销**，所以速览和纪要永远拿不到正文。

### 17.5 改动

`SummaryEngine.swift`：

- 预算提为具名常量并留出充裕余量（**注释写清了实测依据，别再往下调**）：
  - `chapterTokenBudget = 8_000`（单章摘要，原 1 800）
  - `analysisTokenBudget = 16_000`（综合分析，原 6 000）
  - `probeTokenBudget = 2_048`（连通性测试，原 **16** —— 推理模型光思考就要几百 token，
    16 会让「测试连接」假失败）
- 新增错误 `budgetExhausted(Int)`：流式/非流式都解析 `finish_reason`，
  遇到 `length` 且正文为空就归到这里，**文案直接告诉用户换非推理模型**，
  而不是含糊的「没有返回内容」。
- 重试循环遇到 `budgetExhausted` **自动翻倍预算**（最多 2 次，封顶 32 000）。
  抬预算算「换个方式再试」，不占用正常的失败重试次数。

## 十八、深夜模式适配 + 设置里的「外观」开关（2026-09-12，v0.6.0）

### 18.1 问题：一屏两套语言

用户贴来两张 22:05 的截图（系统已是深色），暴露出来的是同一类病：

- 设置面板的页头是**系统画的深色**（`sheet` 顶部），底下却是 `AppTheme` 写死的**浅色纸面**，
  深底配深墨字，「设置」两个字直接看不见；
- 标题栏被系统画成深色，右侧「导入音频 / 设置」按钮底却是浅色 `paper`，浮在深色栏上像一块补丁。

根因很清楚：`AppTheme.swift` 里 15 个颜色值**全部写死成浅色**，而 macOS 的标题栏、sheet 页头、
滚动条、右键菜单是 **AppKit 自己按系统外观画的**。App 一层浅色、系统一层深色，就打架。

### 18.2 做法一：把 15 个 token 全换成动态色

不新增第二套色板（那会变成两条维护线），而是把每个 token 包成
`NSColor(name:dynamicProvider:)`，闭包里按外观分流：

```swift
private static func dynamic(
    light: (CGFloat, CGFloat, CGFloat),
    dark: (CGFloat, CGFloat, CGFloat)
) -> Color {
    Color(nsColor: NSColor(name: nil) { appearance in
        let isDark = appearance.bestMatch(from: [.aqua, .darkAqua]) == .darkAqua
        let value = isDark ? dark : light
        return NSColor(calibratedRed: value.0, green: value.1, blue: value.2, alpha: 1)
    })
}
```

SwiftUI 每次绘制都按当前 `NSAppearance` 取值，所以**运行时切外观自动跟随**，不需要重建视图。

⚠️ **浅色档的数值必须逐字节不动。** 这次改动允许「深色是新的」，但不允许「顺手把浅色调好看一点」
—— 浅色是已经被验证过的基线，一动就要重验一遍。改完 `git diff` 里浅色三元组应当零变化。

### 18.3 新增 / 分叉的 token

原来「一块灰底」既当按钮底盘、又当分段选中、又当图标底，深色下这三件事需要不同的对比度，
所以拆开：

| token | 用途 | 深色值 | 对面 |
|---|---|---|---|
| `controlSurface` | 标题栏次级按钮底盘 | `#474D5B` | 对纸面 1.93:1 |
| `controlEdge` | 次级按钮 1pt 描边 | `#525A6A` | 浅色档 == `controlSurface` 本色（即不可见） |
| `segmentSelected` | 分段控件选中的凸起段 | `#343944` | 对轨道 `#0A0B0E` |
| `graphite` | 深色面板（转写中卡片）**角色互换** | `#3E434E` | 浅色下是压暗板，深色下变抬升亮面 |
| `accentFill` | 品牌色**当底**（配白字） | `#276BFA` **钉死** | 见下 |
| `dangerFill` | 危险色**当底**（配白字） | `#DA343D` **钉死** | 见下 |

**这是本轮最值钱的坑：品牌色要分叉成「当字」和「当底」两个 token。**

- `accent` 当**文字/图标**用：深色下浅纸面若还用 `#276BFA`，对比度只有 2.9:1，读不清；
  必须提亮到 `#76A9FF`（对深纸面 **7.5:1**）。
- `accentFill` 当**底色**（上面压白字）用：如果跟着 `accent` 一起提亮到 `#76A9FF`，
  白字掉到 **2.6:1**，按钮上的字反而糊了。所以 `accentFill` **钉死 `#276BFA` 不随外观变**。
- `danger` / `dangerFill` 同理分叉。

一句话：**同一个品牌色，「当字」随外观变、「当底」不动。** 混用一个 token 必然顾此失彼。

### 18.4 做法二：进程级切换外观（不要用 `.preferredColorScheme`）

设置里的三档开关**不能用 SwiftUI 的 `.preferredColorScheme`**。它只覆盖 SwiftUI 内容层；
本 App 出问题的恰恰是**标题栏和 sheet 页头**这些 AppKit 自己画的 chrome —— 用
`.preferredColorScheme` 会出现「正文翻成深色了，标题栏还是另一套」的鬼样子，等于没修。

正解是设**进程级 appearance**，并把已存在的窗口一起改：

```swift
@MainActor
static func apply(_ appearance: AppAppearance) {
    let target = appearance.nsAppearance          // .system → nil
    NSApplication.shared.appearance = target
    for window in NSApplication.shared.windows { window.appearance = target }
}
```

- `@MainActor` **必须加**：`NSApplication.appearance` / `NSWindow.appearance` 是 MainActor 隔离属性，
  Swift 6 严格并发下非隔离上下文改会直接编译失败
  （`main actor-isolated property 'appearance' can not be mutated from a nonisolated context`）。
- `.system` 档映射成 `nil`，把「跟随系统」的球踢回给 macOS。

### 18.5 持久化

- `UserDefaults` 键 `meetingScribe.appearance`，存 `rawValue`（`system`/`light`/`dark`）。
- **坑**：`init` 里给属性赋值**不触发 `didSet`**，所以启动时要另外补一次 `apply`：
  ```swift
  let stored = AppAppearance(rawValue: UserDefaults.standard.string(forKey: Preferences.appearance) ?? "") ?? .system
  appearance = stored
  AppAppearance.apply(stored)   // init 不触发 didSet，这里补一刀
  ```

### 18.6 设置面板新增「外观」分组

三选一（跟随系统 / 浅色 / 深色），放在设置列表**最后**（模型与转写是常改项，外观是设一次就不动的）。

这里顺手抽了一个复用组件 `WorkbenchSegmentStrip<Item: Hashable>`：结果页那三个 Tab
和设置里的外观三选一**画法逐字一致**（同样的 2pt 轨道内缩、`segmentRadius - 2` 的凸起段、
1pt `rule` 描边、选中态 `semibold`）。本来结果页就有一套自绘分段控件，再抄一遍必然漂移，
所以直接抽出来共用。设置面板顶部副标题也改成「…下面配置**外观**与会后整理使用的模型。」

### 18.7 用户反馈：右上角按钮看不出是按钮

这是本轮唯一一次用户实测回退。深色下 `controlSurface` 旧值 `#343842` 对纸面只有 **1.39:1**
（macOS 自家无边框按钮约 1.25:1，按理不算离谱），但用户仍读不出「这是个按钮」。

两手一起上：

1. 底盘提亮到 `#474D5B`（对纸面 **1.93:1**）；
2. 补一条 1pt 描边 `controlEdge`，**浅色档下它与底盘同色（即不可见），深色档才浮出来**——
   用同一个 token 表达「浅色不需要边、深色需要边」，不写 `if isDark` 分支。

实测（截图像素）：按钮底盘 `#484D5B` vs 标题栏底 `#262826` = **1.75:1**，按钮边界清晰可辨。
描边加在 `WorkbenchLightButtonStyle` 里，条件是 `tint == nil`（带 tint 的主操作按钮不需要描边）。

### 18.8 验证手法（含两个会骗人的坑）

## 十九、标题栏排布 / 底栏分割线 / 空态不再重复提醒 + 「重试」按钮（2026-09-12，同 v0.6.0）

这一轮全部来自用户对着深色版实机截图提的三条 + 一条新想法。

### 19.1 副标题去掉服务商名

用户：「导航栏不要显示『自定义兼容接口』这个字段」。

副标题当时是 `2026/9/12 0:26 · 18:18 · 已完成 · 自定义兼容接口 · deepseek-v4.1-flash`。
最后那一截来自 `analysis.summaryModel`，而它存的是 `SummaryModelSettings.displayName`，
格式是 `<服务商> · <模型名>`。

**关键决定：裁的是展示层，不是存储层。** 新增 `MeetingAnalysis.modelLabel` 只做展示裁剪，
`summaryModel` 原样保留 —— 设置面板要靠完整名字交代「这套凭据连的是谁」，
历史数据也不该被改写。`modelLabel` 按第一个 ` · ` 切一刀，只取模型名；
没有分隔符时原样返回（本地规则档存的就是纯标题「本地保守整理」）。

`summaryModel` 全项目只被 `metaLine` 一处消费，所以改动面很小。

回归护栏：`Tests/MeetingScribeTests/MeetingAnalysisModelLabelTests.swift`（6 条），
覆盖裁切、无分隔符原样、空/全空白判 nil、分隔符后为空时退回、前后空白 trim，
以及一条端到端的「副标题不含服务商名、含模型名」。

### 19.2 标题栏三颗按钮：1pt 的「贴一起」

用户：「右侧的操作按钮很怪，不规范，贴一起了，尤其深夜模式下，而且还有重叠的地方」。

**先说测量结果（像素核验，2× 截图）**：三颗按钮之间只隔 **1pt** ——
导入音频胶囊右沿 x=2430、开始录音左沿 x=2433，中间 2px@2x；
开始录音与齿轮之间同样 1pt。所以用户的感受是准的，它们确实是贴着的。

⚠️ **注意别被「重叠」这个说法带偏**：实测**没有几何重叠**，两两之间各留了 1pt。
用户看到的「重叠」是**贴太近 + 深色下底盘与标题栏明度接近**共同造成的观感，
不是真的压在一起。所以修的是间距，不是层级。

**根因**：三个动作当时是**三个并列的 `ToolbarItem(placement: .primaryAction)`**。
macOS 会把同一 placement 的相邻 toolbar item 收成「一组」，组内间距由系统拍板，
不听你的。而我们用的是自绘 ButtonStyle，不是原生 toolbar button，
系统给的这组间距就是 1pt。

**正解**：三个动作装进**同一个** `ToolbarItem` 里的 `HStack(spacing: AppTheme.space2)`。
间距从此由我们说了算，也不再受工具栏分组启发式影响。8pt 是 macOS 工具栏项目之间的
标准间距。

实测（同一口径复测）：间隙 **1pt → 9pt**。9 而不是 8，是因为次级按钮那条 1pt `controlEdge`
描边以边线为中心画，向外各溢出 0.5pt，两颗就是 1pt。整排因此左移 17.5pt（两颗各多让出 8pt）。

**顺带提醒（差点误判）**：这次对比截图里，标题栏底材色从 `#262826` 变成了 `#393A3A`，
一度以为是 `ToolbarItem` 结构变化带来的回归。**其实是窗口焦点差异** ——
修改前那张窗口没激活（红绿灯是灰的），修改后那张是激活态（红绿黄）。
**验证 macOS 标题栏时，两张截图必须同为激活态**，否则连标题字色都会不一样。
所以本次改动**只**影响间距，标题栏材质没有任何变化。

### 19.3 底栏分割线：去掉

用户：「下方去掉分割线」。

底部播放条原来是 **`paperSoft` 底 + 顶部一条 1pt `rule` 发丝线**
（`WorkbenchAudioPlayerBar` 的 `.overlay(alignment: .top) { Divider() }`）。
像素核验：过渡是 `#1D2026`（纸面）→ `#484D58`（发丝线，1pt）→ `#353943`（`paperSoft` 条底）。

这是把「换个底色」和「画条边界」两件事都做了，底部因此多出一道横杠。
去掉线之后只留底色这一档信号：`paperSoft` 对纸面本身就有反差（深色档 1.41:1），
分区已经够了 —— Finder / Music 的底栏也是这个口径：**边界交给色差，不交给线条**。

实测：过渡变成 `#1D2026` → `#353943`，中间的 `#484D58` 消失。

### 19.4 空态不再重复「没生成结果」

用户：「如果后续实在未生成结果，速览+纪要板块内不要显示这个提醒，因为下面已经显示未出现结果了」。

原来「速览」「纪要」两个板块里，`summaryError` 非空就无条件挂一条
`WorkbenchSummaryFallbackNotice`，而它的正文是
「整理模型未返回，已保留逐字稿；**下面仅显示本地保守结果**」——
**下面什么都没有的时候，这句话就是在替空态重复一遍「没生成出东西」**，
而空态说得更完整（带原因、带出路）。同一屏两处说同一件事。

**修法：给提示加一个出现条件 —— 下面真有本地保守结果才给。**

```swift
if let summaryError = session.analysis.summaryError, !summaryError.isEmpty, hasVisibleContent {
    WorkbenchSummaryFallbackNotice(message: summaryError)
}
```

`hasVisibleContent` 与空态的出现条件**严格互补**，写在各自 document 里：

| document | `hasVisibleContent` | 空态出现条件 |
|---|---|---|
| `WorkbenchOverviewDocument` | `!overviewText.isEmpty \|\| !timeline.isEmpty` | `timeline` 空 **且** `overviewText` 空 |
| `WorkbenchMinutesDocument` | `!minutesText.isEmpty \|\| !decisions.isEmpty \|\| !actions.isEmpty` | 三样全空 |

**顺带修掉一个会因为这次收敛而暴露的错话**：`WorkbenchMinutesDocument` 的空态文案
原来写死一句「本地转写已经完成，但当前**没有使用会后整理模型**」。撤掉提醒横幅之后，
这句话就成了这一屏**唯一**的解释 —— 而模型**用过却失败**的时候它是错的：
用户被告知「没配模型」，于是跑去设置里翻半天，其实模型配得好好的。
所以两个 document 的空态文案都改成**认得出「为什么空」**：

- 失败过 →「整理模型这次没有返回可靠结果，原文仍然保留。可以直接重试，或者更换…」
- 没配模型 →「当前没有启用会后整理模型。…」

### 19.5 新增「重试」按钮（用户提议，采纳）

用户提议：「在缺省图区域现在配置模型按钮左侧增加一个【重试】按钮？点击可以重试让 AI 加载速览/纪要？」

**采纳。** 这个提议解决的是一个真实的可达性问题：此前唯一的「重新整理」入口是
结果页 Tab 行**最右侧一个裸 ↻ 图标**（`WorkbenchResultTabBar.pageActions`），
它离「失败」这件事发生的地方（正文中间的空态）隔了整整一屏，
而且是一个没有文字的图标 —— 用户看着「没有生成速览」，很难联想到右上角那个小箭头是出路。

实现要点：

- `WorkbenchSummaryEmptyState` 增加一个**可选**的 `retry: (() -> Void)?`；
- **只有真的失败过（`summaryError != nil`）才给这颗按钮**。没配置模型时点「重试」还是同一个
  结果，那种情况该做的是去设置里挑个模型 —— 多一颗按钮只会让人白点一下。
  所以由调用方按失败与否决定给不给，组件本身不猜。
- 顺序按用户要求：**重试在左**。视觉权重上给重试**实底主色**
  （`WorkbenchLightButtonStyle(emphasized: true)`），
  「打开设置选择模型」留描边 —— 因为多数失败是预算/网络这类一次性的，重试是最省事的一步；
  去设置换模型是退一步的做法。
- 两颗按钮共用同一个 `regenerateSummary(for:)`，与 ↻ 图标**同一条代码路径**，没有新增分支。
- 点击前的前置条件是 `regenerateSummary` 里原有的守卫
  （`status == .ready`、不在录音/处理中、逐字稿非空）。实测本机上出问题的那场会议
  `status=ready`、135 段逐字稿，守卫全过 —— 点下去会真的发起请求，不会被静默吞掉。

⚠️ **本机 GUI 自动化权限仍被拒，所以「点一下」这个动作我没法代劳** ——
上面能验到的是「按钮渲染出来了、前置条件全过、走的是既有代码路径」，
真正的点击需要用户自己试一次。

### 19.6 本轮遗留 / 可继续做

- **提醒横幅里也可以放一颗重试**（`hasVisibleContent` 为真、也就是下面真有本地保守结果时）。
  那种情况现在仍然只有 Tab 行最右侧那个 ↻ 是出路，同样偏僻。本轮按用户范围只做了空态，
  这一处留着待拍板。
- 本机 5 场历史会议里有 3 场失败原因是 `总结模型连接失败：网络连接已中断`
  （长请求被中间环节按空闲超时掐断）、1 场是 `总结模型没有返回内容`（v0.5.1 的 token 预算坑）。
  两类都是**重试很可能直接救回来**的，这也是这颗按钮价值的直接证据。

## 二十、纪要页撤掉提醒横幅 + 原文页排版精修（2026-09-12，v0.6.1）

用户对着实机截图提了两条：
① 「纪要下也不要这个提醒」；② 「原文页面下，因为文字大小啥的显得没有质感，不精致，调整下」。

### 20.1 纪要页：横幅撤掉，原因并进那条本地说明

「速览」和「纪要」原来各挂一条 `WorkbenchSummaryFallbackNotice`。上一轮（§19.4）已经给它加了
`hasVisibleContent` 条件，解决的是「横幅 vs 空态」重复。**但纪要页还有第二重重复**：

| 位置 | 说的是什么 |
|---|---|
| 提醒横幅 | 整理模型未返回，已保留逐字稿；**下面仅显示本地保守结果**。 |
| `WorkbenchLocalSummaryNote` | **本地保守整理**只保留逐字稿中明确命中的决策和待办，不把普通讨论拼成纪要。 |

两句话都在解释「下面这些为什么是本地结果」，观感上是这一页在反复道歉。用户直接点名：
纪要下不要这个提醒。

**做法：纪要页整段删掉横幅**（连 `hasVisibleContent` 一起删，不再有第二个消费者），
把失败这件事交给那条本地说明 —— `WorkbenchLocalSummaryNote` 增加可选入参 `failureReason`：

- **没值**（用户主动选了本地规则档，或者压根没配模型）：保持原样，绿勾 + 灰色说明，
  一句「本地保守整理只保留…」；
- **有值**（模型失败过）：图标换成 `info.circle` + 警示色，主句改成
  「整理模型这次没有返回结果，下面是本地保守整理：…」并用 `ink` 提高到正文权重，
  小字补上真实错误（`summaryError`，可从「网络连接已中断」到「总结模型没有返回内容」）。

**为什么原因必须跟着搬过去**：横幅撤掉之后，这条说明就是这一页唯一讲得清
「为什么下面是本地结果」的地方。原因要留在屏幕上（§19.4 已经为此把 `.help` 换成可见小字），
不能因为撤横幅而把信息一起丢掉。

**「速览」页的横幅保留。** 它跟纪要不一样：速览没有等价的本地说明，横幅是那里唯一的交代。
（`overviewText` 与 `timeline` 都只由模型产出，本地规则档两者都是空 —— 所以这个分支多数时候
走不到，留着当兜底。）

⚠️ **仍未做**：本地结果 + 失败时，重试入口依然只有结果页 Tab 行最右边那个裸 ↻。
用户这轮的方向是「少放东西」，所以没有顺手加按钮。

### 20.2 原文页：为什么原来"没有质感"

先量了用户那张截图（2× 像素），原来的参数是：

- 正文 **17pt** + `lineSpacing 5`（行距 ≈ 1.5 倍，行内间距 51px@2x）；
- 时间戳 `.caption` + `frame(width: 92)`，与正文 **`.top` 对齐**；
- 置信度是 `.caption` 的裸百分比，飘在最右边，和时间戳同色同字号；
- 行内上下留白各 **16pt**，行间是**通栏** 1pt 分隔线。

四条叠起来的效果：**一行字大、留白足、三列同字号、线穿到底** —— 像放大字号后的纯文本清单。
"不精致"的观感主要来自三处**没做对齐**，不是来自字号本身。

### 20.3 改法（四处，都可实测）

| 改哪 | 原来 | 现在 | 为什么 |
|---|---|---|---|
| 正文 | 17pt / lineSpacing 5 | **14.5pt / lineSpacing 4.5** | 逐字稿是**参考面**，不是阅读面：速览 20pt、纪要 18pt，原文压到 14.5pt 才有层级 |
| 时间戳栏 | 92pt，`.top` 对齐 | **56pt + 间距 16pt，`.firstTextBaseline` 对齐** | 11pt 的「00:00」只占约 30pt；92pt 是白留的。`.top` 会让小字浮在行顶（比正文高半行） |
| 置信度 | 裸数字右飘 | 11pt 常规字重，`frame(width: 40, alignment: .trailing)` | 让它和一堆同样的数字落成一列 |
| 行内留白 / 分隔线 | 16pt / 通栏 | **12pt / 从正文列起笔** | 左边那一栏留白是给时间戳的，横线不该穿过去 |

**基线对齐是本轮最值钱的一处**。实测（2× 像素，第一行）：

```
时间戳墨迹  y 413..430
正文首行墨迹 y 406..432     ← 底边 430 vs 432（基线基本齐）
置信度墨迹  y 413..429
```

小字的下沿与正文首行齐平、上沿低 3.5pt —— 这正是「11pt 挂在 14.5pt 的基线上」的样子。
`.firstTextBaseline` 穿过 `.frame(width:alignment:)` 是生效的（frame 会转发子视图的基线）。

**内缩分隔线**：`WorkbenchTranscriptDocumentRow.bodyColumnInset = 56 + 16 = 72`，
`Divider` 加 `.padding(.leading, 72)`，与正文列同一竖线。实测线体横跨
x 958..2653（逻辑 479..1326.5），正文列左沿 x=962（逻辑 481）—— 对齐误差 1pt 以内。
（只有原文页这么做：别的页的行首没有时间戳栏，通栏线才是对的。）

**页眉降级为眉标**：`2026/9/12 0:26 · 原汁原味保留转写` 从 18pt 常规灰改成
**12pt 中等字重、日期用 `muted`、标签用 `ink`** 的两段式一行。页面主角是下面成百上千行
逐字稿，眉标不该跟它抢字号。实测眉标左沿 x=818、时间戳 x=815（都在内容列左边线）。

### 20.4 对比度实测（改成 11pt 之后更要看这个）

| | 纸面 | 正文 | 时间戳 / 置信度 |
|---|---|---|---|
| 深色 | `#1D2026` | `#F3F5F8` → **14.94:1** | `#B6BDC9` → **8.63:1** |
| 浅色 | `#FAFBFD` | `#242931` → **14.12:1** | `#788393` → **3.71:1** |

⚠️ **浅色档的 11pt 元信息只有 3.71:1，低于 WCAG AA 对正文的 4.5:1。** 这是**既有问题**
（时间戳原来就是 `.caption` + `muted`，本轮没动它的颜色），但从 11pt 的比例看更该修。
修它的代价是动**全局** `muted` 的浅色值 —— 会连带改掉侧栏副标题、会话元信息、各处说明文字，
所以本轮**没有擅自动**，留给用户拍板：要么加深 `muted`（浅色档），要么给「小字元信息」
单独一个比 `muted` 深一档的 token。

### 20.5 附带发现：本机 GUI 自动化权限恢复了

之前几轮一直是「`System Events … 权限违例 (-10004)`，合成点击送不到窗口」，只能用环境变量夹具
或临时改默认值来截图。**这一轮实测可以直接驱动 UI 了**：

```bash
# 键击（用来关掉钥匙串弹窗）
osascript -e 'tell application "System Events" to key code 53'
# 按元素点（比坐标稳，输出里会把命中的控件路径打回来）
osascript -e 'tell application "System Events" to tell process "MeetingScribe" \
  to click button 1 of group 2 of splitter group 1 of group 1 of window 1'
```

于是**夹具不再是唯一办法**：结果页三个 Tab 可以直接点着抓图。
（本轮仍用了两次夹具，但那是因为当时还不知道点击可用；以后再改这 App 的 UI，
优先直接点，别再加夹具。夹具一旦加上，就必须反向撤销 + `grep` 复核残留为 0。）

另外：**每次重新打包后启动，macOS 都会弹一次钥匙串授权**
（`MeetingScribe 想要访问你的钥匙串中的密钥 MeetingScribe.summary-model`，
自签名证书换了新二进制、ACL 不匹配）。它会**挡在窗口前面**，让截图拍到的是弹窗而不是界面。
用 `key code 53`（Esc）关掉即可；不影响界面渲染，也不影响本轮任何验证。
