# 第一性原理审查：MeetingScribe 的问题与 UI/用户体验

> 审查日期 2026-09-15。审查对象不是"某个界面哪里丑"，而是**"审查这件事本身"在当前做法下能不能收敛**。
> 全部结论只由四类输入推导：已确认事实、未验证假设、真实目标、现实约束。行业惯例与现成方案按下不表。

---

## 0. 结论先行

当前做法的结构特征是：**按"轮次"记录、按"症状"修复、按"改动是否落地"验收。**
这三件事各自都不能收敛：

- **症状 ≠ 根因**：一个症状可对应 N 个断因，一个断因也可对应 N 个症状。
- **轮次是时间轴，不是状态空间**：判断"某功能现在是什么行为"必须按时间顺序翻 24 章。
- **"落地"与"正确"是两件事**：前者可以自动验证（md5、测试、像素），后者当前只靠用户的眼睛。

推导出的新路径一句话：**把这个 App 的所有状态穷举成一张有限表，让每个状态自解释；验收单位从"轮次"改成"状态"。**

## 一、已确认、无法绕开的基本事实

这些不是流程问题，是物理约束。任何方案绕开它们都会退化。

| # | 事实 | 证据 |
|---|---|---|
| F1 | **感知通道只有用户的一双眼睛。** 写代码的一方读不了图；本机无「辅助功能」授权，点不动、滚不动、hover 不了。 | `CGEvent` 注入的滚轮/点击被静默丢弃（注入前后像素完全相同）；`Read` 打不开 RGBA 剪贴板 PNG。全部 UI 轮次都靠"装上去 → 用户看 → 用户报"。 |
| F2 | **一次反馈往返成本很高。** 改代码 → 编译 → 签名 → 装 `/Applications` → 用户杀旧实例重开 → 看 → 用语言描述。 | 2026-09-14 一次会话内，左侧空态**一处位置**来回 3 次（贴左上 → 居中 → 上移 40px → 再上移 40px）。 |
| F3 | **用户报的是症状，不是根因。** 这不是用户的问题，是语言的极限——人能描述的只有"我看到什么"。 | 「还是弹这个授权」真因＝后台读钥匙串密文；「刚导入的音频不能播放」真因＝播放候选把 `input.wav` 排在原始音频前；「缺省图没了」真因＝空态被塞进 `ScrollView` 的列表流里。三次都不在同一层。 |
| F4 | **测试只能证明不变量，证明不了体验。** | 184 测试全绿时，导入音频仍不能播、空态仍缺图、钥匙串仍弹窗。测试判据是"逻辑对不对"，用户判据是"这次用起来顺不顺"。 |
| F5 | **数据是真实会议数据。** 不能当测试场地；同时老会话必须永久读得出来。 | §二十三数据丢失事件；§24.8「加字段必须 Optional + `encodeIfPresent`」。 |
| F6 | **模型与权限是外部依赖，不由这个 App 决定。** 麦克风、系统音频、摘要 API Key、模型可用性，四项都可能缺失。 | §二录屏权限、§三模型发现状态机、§24.6 摘要模型端点。 |
| F7 | **只有一个人做产品/设计/开发/测试/验收。** 没有 QA、没有设计评审、没有可用性被试。 | 项目实际协作形态。 |

**F1 + F7 的合成推论（后面全部推导的支点）：**
感知与验收都只有一个人时，**App 自己不说清楚的状态，必然变成一次未来的报修。** 换句话说：用户看不见的状态 = 已欠下的 bug。

## 二、习惯性接受、却未验证的假设

| # | 假设 | 被什么否证 |
|---|---|---|
| A1 | **「用户报一个点，修掉它，体验就前进一步。」** 假设症状与缺陷一一对应。 | F3 直接否证。提交历史留下痕迹：`3d2699c`（避免后台弹钥匙串）与 `c2097f1`（后台不再读钥匙串）是**相邻两次修同一症状**；`58d27ac` 的提交标题直接写着"同一个「没有标签」的**第二个**断因"。 |
| A2 | **「测试通过 = 这版可以交给用户。」** | 每次交付后用户都能立刻找到新的可见问题。184 绿只证明"改的东西进包了"。 |
| A3 | **「先把功能做完，UI 统一美化留到后面。」** | §六「仍未处理」写于 2026-09-11，到 09-15 跨 **6 个版本 tag** 仍挂着同样的两条（播放条对齐 800 列、约 60 处散乱间距）。**"后面"从未到来，因为它没有触发条件。** |
| A4 | **「文档章节越多 = 问题治理得越好。」** | §一~§二十四 全部以"轮次"组织。轮次记录的是**我做了什么**，不是**系统现在是什么状态**。副作用已出现：§24.1 写"当前 **171** 条测试"，实测已是 **184**——权威副本自己先漂移了。 |
| A5 | **「主色/对比度/间距属审美，可最后统一。」** | §24.7 已实测：`success` 当 11pt 正文在浅色下只有 **2.75:1**（AA 要 4.5:1）。这是可用性不是审美。而护栏句「浅色档是已验基线，不准动」恰恰把"11pt 元信息不达标"锁在基线里**合规地不许修**。 |
| A6 | **「死代码无害。」** | `ContentView.swift` 全文 **714 行**，里面是**一整套与活代码平行的第二套 UI 词汇表**：`LegacyContentView`、`SettingsView`、`SessionRowView`、`SessionDetailView`、`DecisionSection`、`ActionSection`、`TimelineRow`、`StatusBadge`… 与活代码的 `WorkbenchSessionRowView` / 活的设置面板近同名、同处一个 module、共享 `AppTheme` 与同一批模型。**改错文件不会报错**——这是下一个"改了没生效"的现成种子。 |

## 三、真正想实现的目标

先剔除三个假目标：

- **假目标 A：**「做一个好看的 macOS App」。好看是结果，不是目标。
- **假目标 B：**「把所有已知 UI 问题清零」。清单永远补不完（F3 保证还会有新症状）。
- **假目标 C：**「通过更多测试」。测试数在涨，用户抱怨没有相应减少。

真目标（从 F1~F7 反推，只有一个）：

> **用户在一次真实会议的全过程里，不需要为这个 App 的任何一个状态分心。**

拆成三条可判定的：

| | 目标 | 判据（用户视角） |
|---|---|---|
| G1 | **不出错** | 录了就有、转了就出、出的能用 |
| G2 | **不疑惑** | 任何时刻看屏幕，都知道"现在在干嘛 / 下一步会发生什么 / 卡住该点哪" |
| G3 | **不返工** | 失败或缺失时，知道确切原因，并有一条走得通的路——而不是猜、不是重试到麻木 |

**关键推论：** 由 F1 + F7，目标 G2 实际上就是产品本身：

> **App 自己的状态面 = 产品。** 每一个能进入的状态都必须有完整、自解释、不用猜的渲染。做到这一点，用户的报修才会从"你猜"变成"它已经告诉我了"。

## 四、现实中的资源与约束

| 类别 | 约束 |
|---|---|
| 人力 | 1 人（产品＋设计＋开发＋测试＋验收） |
| 感知 | 我无视觉、无点击、无滚动；用户有眼，且只有眼 |
| 往返 | 一轮 ≈ 编译＋签名＋安装＋人工看（分钟级），**且必须用户在电脑前** |
| 技术 | Swift 6 / SwiftUI / macOS 15+ / Apple Silicon；`-warnings-as-errors` 使废弃 API 直接编译失败 |
| 数据 | 不得拿真实会议数据当夹具；老会话必须永久可读（F5） |
| 外部 | 麦克风/系统音频权限、API Key、模型端点可用性均不可控（F6） |
| 分发 | 自签 `PM Studio Signing`，无 Developer ID → 给别人用需公证（未做） |
| 文档 | 24 章、约 13.4 万字，已超出"能读"的体量；长期记忆有注入上限，只能放指针 |

## 五、输出 1：原方案中只在修补表面的部分

公平地说，原方案有三件事是对的，必须保留：**实测纪律**（像素扫描/OCR/md5，不靠"我觉得"）、**根因记录**（每章都写了真相而非症状）、**回归护栏**（184 测试 + 老数据夹具）。问题不在严谨程度，在**结构**。

| # | 表面修补 | 为什么它只是补表面 |
|---|---|---|
| 1 | **按症状修，不按状态修** | 24 章的共同结构都是"用户报 A → 在 A 的渲染处改 A"。同一症状会复发（`3d2699c`/`c2097f1`），或一个断因修完还剩第二个（`58d27ac`）。 |
| 2 | **用"轮次"当治理单位** | "轮"是时间，不是状态。查一条行为必须按时间读 24 章，且副本已经开始漂移（171 vs 184）。 |
| 3 | **验收靠"改到了"** | md5 一致 + 测试通过 + 像素扫到色块 → 证明**改动落地**，不证明**改动正确**。侧栏空态：代码对、哈希对、测试全绿，位置错了 3 次。 |
| 4 | **"仍未处理"清单没有触发条件** | §六 item 4/5 挂 4 天、跨 6 个 tag。"以后统一处理" = 永不处理。 |
| 5 | **把可用性归进审美队列** | 11pt 元信息 2.75:1、播放条不对齐 800 列，被排到"细节/美化"后面，实际属于 G2/G3。 |
| 6 | **护栏本身在制造欠账** | 「浅色档不准动」让对比度不达标合规地留在基线里——护栏保护了基线，也冻结了基线里的缺陷。 |
| 7 | **死代码当无害** | 714 行平行 UI 词汇表，是"改错文件不报错"的现成陷阱。 |

**一句话：原方案在"怎么改得更准"上做到了极致，但没有回答"下一次该看哪里"。**

## 六、输出 2：从基本事实重新推导出的新路径

推导链（每一步只用到上面的事实）：

1. F1 + F7 → 用户是唯一的验收器。
2. F3（用户只能报症状）+ F2（往返很贵）→ **"让用户看"这一步必须被前置**：不要等用户撞到，先让 App 自己把状态说清楚。
3. 于是路径反转：**从「用户报 → 我改」，变成「我先把状态穷举出来 → 让每个状态自解释 → 用户只在'它没告诉我'时才报」。**

**三步：**

### 第一步：把 App 的状态穷举成一张有限表（取代继续攒轮次）

App 可进入的状态是**有限**的：空闲 / 录音中 / 转写中 / 整理中 / 成功 / 失败 / 被前置门禁拦下 / 缺麦克风权限 / 缺系统音频权限 / 缺 API Key / 模型不可用 / 音频文件缺失 / 音频不可播 / 历史老数据。

对每个状态定义三列，**放在一处**（不是散在 24 章里）：

| 状态 | 屏幕上显示什么字 | 能点什么 | 点了变成哪个状态 |
|---|---|---|---|

判据：任何时刻，用户看屏幕都能回答"现在在干嘛 / 下一步会发生什么 / 卡住该点哪"。

### 第二步：把"用户看不见的状态"列为最高优先级缺陷

因为 F1：看不见的状态 = 未来的报修。排序规则从"用户报的先后"改成"**哪个看不见的状态在真实使用中会先撞上**"。

这条规则直接重排现有待办：

| 原序号 | 项 | 新排序 | 理由 |
|---|---|---|---|
| ⑨ | 模型发现状态机 | **最先** | 用户看不见模型在不在，是纯状态缺失 |
| ③ | 死代码 714 行 | **第二** | 会污染此后**每一次**改动（A6） |
| ⑧ | 录屏权限硬门禁 | 第三 | 缺权限＝用户看不见的状态 |
| ① | 浅色 11pt 对比度 < AA | 第四 | 可用性，非审美（A5） |
| ② | 横幅重试 | 第五 | G3 入口 |
| ④⑤⑥⑦ | 侧栏行高 / 空态副标题 / 播放条对齐 / 间距统一 | 最后 | 纯观感，不改变"会不会撞到看不见的状态" |

### 第三步：把"证明落地"与"证明正确"分开，并给后者一个不靠用户眼睛的手段

- **落地**：现有做法已够（md5 / 测试 / 像素扫描）。
- **正确**：改用**状态遍历**——用现成夹具（`.onAppear` 置状态 / `@State` 初值 / `defaults write` / `MS_DATA_ROOT` + `.defaultScrollAnchor(.bottom)`）把每个状态渲染出来，逐状态核对"文案 / 可点项 / 下一跳"。

关键是**逐状态**而不是逐轮次：一次会话能覆盖 N 个状态，而不是靠 N 次往返（直接对冲 F2）。

## 七、输出 3：这条路径成立的前提

任一不成立，路径就退化回原方案。

| # | 前提 | 现状评估 |
|---|---|---|
| 1 | **状态可穷举** | 基本成立：代码里已有显式 `status` 枚举（`.failed/.processing/.recording/.ready`）；但"缺权限/缺 Key/无音频/老数据"目前是**隐式**的，需要补成显式。 |
| 2 | **每个状态都能被夹具渲染** | 成立：手法现成，但必须遵守既有纪律——截完还原 + `git diff` 复核 + 交付写明"哪个动作本身没被实测"。 |

| 6 | **死代码先清或先隔离** | 未做。不清则"改了没生效"会继续发生。 |

## 八、输出 4：验证它的第一步

**最小可判定动作：只对"非成功"这一类状态做一次穷举，产出 3~6 行状态表 + 一张实拍矩阵。**

1. 从代码把**非成功**状态枚举出来，至少 4 个：失败 / 缺 Key / 缺权限 / 音频不可用；外加历史老数据 1 个。
2. 每个状态写一行三列：**显示什么字 / 能点什么 / 点了去哪**。
3. 用现成夹具把每个状态渲染出来逐状态核（**这一步不需要用户在电脑前**）。
4. 交给用户看的不是"我又改了几处"，而是**这张表 + 矩阵**，只问一句：
   > **"这几个状态里，有没有哪个的文案或按钮是我说不清的？"**

**判定标准（明确的通过 / 不通过）：**

- ✅ **通过** = 用户在表上指出的是**文案或入口的语义问题**（说明表在起作用，我们能对着条目谈）。
- ❌ **不通过** = 用户说"我还是不知道 X 情况该怎么办"（说明该状态没被穷举到，或它的三列没写全）。

**这一阶段不追求视觉变好看，只追求"状态有没有被说清"。** 它便宜、不需要用户在电脑前、且一次覆盖多个状态。

**为什么是这一步，而不是"先把间距统一了"：**
间距统一是原清单第 7 项，做完不改变"用户会不会撞到看不见的状态"；状态穷举直接减少未来的往返次数——在 F2（往返贵）与 F7（只有一个人）之下，那是唯一能**累积**收益的方向。
