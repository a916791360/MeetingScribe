# 转写 / 速览 / 纪要 质量提升方案

> 2026-09-13 · 基于**本机实测**（不是经验之谈）。所有数据都在本文档里可复算。
> 结论先行：**速览与纪要"很差"的头号原因不是模型不够强，是产出被静默截断后整场降级成本地规则结果**；
> 其次是 prompt 自己把纪要写空了。转写侧最划算的修复是「术语表 + 抑制非语音」，**而网上流传的"加 VAD"在本机反而会变差**。

---

## 0 一句话结论 / 最值钱的四个发现

| # | 发现 | 证据 | 处置 |
|---|---|---|---|
| 1 | **结果被截断 → 静默降级**。`analysisTokenBudget=16_000` 里 70~90% 被思考链吃掉；正文**非空但被截断**时不会触发预算翻倍，`parseAnalysis` 抛错后整场退回**本地规则**（速览/纪要都空） | 实测 A 组 `finish_reason=length`、`reasoning_tokens=14304/15998`、JSON 断在 timeline 数组中间 | **P0**：预算 16k→32k；截断也触发翻倍；截断时保留已解析部分而不是整场丢弃 |
| 2 | **prompt 主动禁止写实质内容**。「纪要正文只写讨论脉络、背景和过程，不要重复列出决策与待办」——这条把纪要掏空成"会上介绍了…讨论随后延伸到…" | 44.6 分钟会议产出**682 字**纪要（压缩比 6.5%），0 个小标题，通篇过程叙述 | **P0**：重写 prompt，改为**按议题分节 + 背景/讨论/结论**，允许（并要求）写实质内容 |
| 3 | **转写侧最划算的是"术语表提示词 + `-sns`"**。同一段音频，标点覆盖率 90%→**100%**，段数 90→75（更完整），"固状系统/多摩泰/收视频/素质"等错词归零 | 实验一 B 组 | **P0**：`--prompt` 注入术语表 + `-sns` + `--carry-initial-prompt` |
| 4 | **直接开 VAD 会让逐字稿更差**。实测段数 90→**273**、有标点段占比 90%→**5.5%**，全部碎成 2 秒短句 | 实验一 C 组 | **P2 且默认不做**；要用必须先调大静默阈值，见 §4.1 |

```

  → buildAnalysis → MeetingSummaryEngine.analyze  MeetingStore:913 / SummaryEngine:78
```

### 2.2 实验一：转写参数三组对照（同一段 0~604 s 音频）

A = 现状参数；B = 加术语表提示词 + `-sns` + `--carry-initial-prompt`；C = 在 B 之上开 VAD（silero v6.2.0）

| 指标 | A 现状 | B 术语+去非语音 | C +VAD |
|---|---|---|---|
| 段数 | 90 | **75** ✅ | **273** ❌ |
| 均字/段 | 34.7 | **41.6** ✅ | 10.1 ❌ |
| 均时长 | 6.48 s | **7.90 s** ✅ | 2.19 s ❌ |
| **有标点段占比** | 90.0% | **100%** ✅ | **5.5%** ❌ |
| 低置信段(<0.4) | 0 | 2 ⚠️ | 7 ⚠️ |
| 均置信度 | 0.79 | 0.75 | 0.74 |
| 最大复读 | 7 | 7 | **3** ✅ |
| 耗时 | (随 App) | 53 s | 84 s |

**专有名词命中（出现次数，越少越好）**：

| 错词 | A | B | C |
|---|---|---|---|
| 固状（→故障） | 1 | **0** | 0 |
| 多摩泰（→多模态） | 1 | **0** | 0 |
| 收视频（→搜视频） | 1 | **0** | 1 |
| 缩这个（→说这个） | 1 | **0** | 0 |
| 素质（→资料） | 1 | **0** | 0 |
| 同弟（→同样） | 1 | 1 | 1 |

**原文对照（0~80 s）**：

```
A 现状：然后呢这是我们的MVP版本 … 客户他既可以通过A来诊断 … 对,固状系统,固件,然后标准现象,直接就入库。
        包括什么呢?…你可以用AI收视频,一些东西都是可以的。

B 术语：继续吧,行。然后这是我们的MVP版本,故障与问题解决中心…客户它既可以通过AI来诊断…
        对,故障系统,故件,然后标准现象,直接就入库。

C VAD ：[0.2] 然后呢,这是我们的MOP版本,故障与问题解决中心…   ← 碎成 2 秒一句，标点基本消失
        [33.4] 所有的知识都是相关联的,它可以直接在右侧…
```

**结论**：
1. **B 是净收益**：句子更完整、标点齐全、专有名词被提示词纠回来了。代价是偶发新错（"固件"→"故件"、一处 "AI生产的"→"AI生存的"）——属于提示词注入的正常代价，可接受。
2. **C（VAD）默认参数下明显更差**。原因：VAD 把音频切成 2 秒级小块分别解码，每块独立**丢掉了跨句上下文**，而 whisper 的标点和句子完整性恰恰来自长上下文。**所以"加 VAD 提升转写"这条流行建议在本机 + 24 kbps 压缩音频上不成立。**
   （VAD 唯一的好处是复读从 7 降到 3，以及 84 s vs 53 s —— 代价太大。）

### 2.3 实验二：逐字稿后处理（纯确定性，零模型成本）

三步：① 术语表替换 ② 复读折叠 ③ 去低置信垃圾段 ④ 按句合并碎片

| 阶段 | 段数 | 总字数 | 均字/段 | 中位字/段 |
|---|---|---|---|---|
| ① 原始（现状） | **871** | 13 037 | 15.0 | 9.0 |
| ② +术语纠错 +复读清理 +去低置信 | 866 | 12 943 | 14.9 | 9.0 |
| ③ +按句合并 | **164** | 12 943 | **78.9** | **71.0** |

术语表在这一场命中 **19 处**（多摩泰×4、重够×3、炫贵×2、前张×2，其余各 1）。

合并前后对照（同一段话）：

```
现状：  [48.0] 呃,属于我们自己的知识库的,自己整理的。
        [51.0] 那自己整理,那这个两个?
        [53.0] 这个规划,就是我和上周…协调了一个那个AI的方案,我们会在周六上线,是怎么个解决逻辑呢?
        [64.0] 就是说,嗯,我们的产品经理…一股脑子塞给AI,由AI所有解析出来。

合并后：[43.0-51.0] 这个话,这个话,他是属于AI生产的,还是我们自己需要去整理的?呃,属于我们自己的知识库的,自己整理的。
        [51.0-64.0] 那自己整理,那这个两个?这个规划,就是我和上周…是怎么个解决逻辑呢?
```

**结论**：**字数没变（13 037→12 943，没有丢内容），但段数降到 1/5.3，逐字稿从"一地碎片"变成可读的句子。** 顺带把喂给总结模型的 `[时间戳]` 行数从 871 降到 164 —— 模型的 prompt 里少 700 多个时间戳噪声，理解成本直接下降。这是**投入产出比最高的一项**。

### 2.4 实验三：速览/纪要 prompt —— 以及一个"事故"

**事故本身比我想要的结果更有价值。**

| 组 | prompt | 预算 | finish | 正文 | 思考链占比 | 结果 |
|---|---|---|---|---|---|---|
| **A 现状** | 现有 prompt | 16 000 | **length** | 3 206 字（**截断**） | 89% | **JSON 断在 timeline 数组中间 → 解析失败** |
| **B 改造** | 新 prompt | 16 000 | length | **0 字** | 100% | 完全无正文 |
| **B1 单次** | 新 prompt + 清洗后逐字稿 | 32 000 | **stop** | **14 306 字** | 70% | ✅ 完整 |
| **B2a 仅速览** | 拆出来的速览 prompt | 16 000 | length | 9 727 字（截断） | 72% | ❌ 仍不够 |
| **B2b 仅纪要** | 拆出来的纪要 prompt | 16 000 | **stop** | 4 470 字 | 75% | ✅ 完整 |

**A 组（现状 prompt）实际截断现场**：正文在 `"timeline": [ {...}, {...` 处被切断。在 App 里这条路径会走
`parseAnalysis` → `JSONDecoder` 抛错 → `SummaryEngineError.invalidStructuredResponse` →
`buildAnalysis` 的 `catch` → 返回 **`MeetingAnalysisBuilder.build()`（本地规则）**，
并且只把 `summaryError` 写进 `analysis`（UI 上只体现在「速览」空态里）。

**也就是说：会议越长越实质，越容易命中截断，越容易整场看到"速览空 / 纪要空"的结果。** 这正是「一个会议下来看到的速览和纪要内容感觉非常差」的直接机制。

**B1 产出（32k 预算）**：

```
【结论】 ASA定9月底跑通售后全链路，周六上线1.1.1
  • 周六上线AI资料解析：维修手册等交AI入库，赵瑞梅协调 [00:51]
  • 周六上线1.1.1：工作台、全局搜资料、AI入口、我的产品学院 [16:59]
  • 9月底目标：查资料/问AI/转工单/找专家/学课程闭环 [31:35]
  • 1.2.0/1.3.0做工单中心和远程专家，待原哥与采购确认 [26:18]
  • 域名改独立域名，不得关联伊勒曲比亚，先运行 [29:16]
  • 多语言视频倾向源头做语言版，英文识别最好 [07:34]
决策 15 / 待办 12 / 待确认 12   （现状：10 / 9 / 0）
```

**B2b 产出（仅纪要，16k）**：

```
## 故障与问题解决中心 MVP 与知识库内容 [00:00]
**背景** MVC 版本…两类入口…
**讨论要点**
 1. 知识来源不是AI自动生产，而是自建知识库整理。AI方案与赵瑞梅协调，计划周六上线…
 2. 用户对真实视频要求高，AI搜视频也被纳入考虑…
**结论** 当前MVP先做知识库发现和AI诊断闭环…

## 用户侧呈现形态：问答、多模态、远程协助与生态链接 [04:07]
…
```

**结论**：
1. **光改 prompt 不改预算 = 更糟**（B 组 0 字）。改造 prompt 一定要配预算提升。
2. **32k 是能跑通的预算**（B1 `finish=stop`）。
3. **拆成两次调用是更稳的架构**：纪要单独调用 16k 就 `stop`（输出只要 4 470 字），推理链压力小得多；速览+决策+待办那次给 24k。
4. 改造后的产出与现状是**代差**：从"话题清单 + 过程叙述"变成"结论 + 带时间锚的信息要点 + 按议题分节的实质纪要"，且多出 `owner` 与 `openQuestions` 两组字段。

## 3 根因清单（分层，带代码位置）

### 3.1 转写层

| # | 根因 | 位置 | 影响 |
|---|---|---|---|
| T1 | `--prompt` 只写"这是一场中文商务会议"，且注释里**刻意不写话题词**，导致领域专名全靠模型猜 | `WhisperPipeline.swift:324` | 多摩泰/公单/固状/前张/专要 等系统性错词 |

| T4 | 逐字稿段边界 = whisper 段边界，无按句重排 | `WhisperTranscript.init` | **871 段 / 中位 9 字**，可读性差，污染下游 prompt |

| T7 | 分块 10 分钟 + 重叠 2 秒，靠 `segment.start` 去重 | `MeetingStore:783-818` | 边界处的半句话无法恢复（2 秒对中文一句偏短） |

| # | 根因 | 影响 |
|---|---|---|

| # | 根因 | 位置 | 影响 |

### P0 — 一天内可做、零架构风险、立刻见效

#### P0-1 逐字稿后处理（本次实测 ROI 最高）

新增一个纯函数 `TranscriptCleaner`，在 `WhisperTranscript.init` 之后、`setupAnalysis` 之前调用：

```swift
// 建议新增文件 TranscriptCleaner.swift（纯函数、可单测、无 IO）
enum TranscriptCleaner {
    /// ① 术语表替换（用户可编辑，见 P1-3）
    /// ② 复读折叠：把「项目卡 项目卡 项目卡」压成一次
    /// ③ 丢低置信垃圾段：confidence < 0.30 且字数 < 8 的段直接丢
    /// ④ 按句合并：条件为「上一段已句末标点 / 间隔 > 1.6s / 累计 > 120 字」，
    ///    目标 40~120 字一句（实测 871 段 → 164 段，字数不丢）
    static func clean(_ segments: [TranscriptSegment], glossary: [String: String]) -> [TranscriptSegment]
}
```

- 实测效果：871 → **164** 段，均字/段 15.0 → **78.9**，总字数 13 037 → 12 943（**不丢内容**）。
- 顺带把喂给总结模型的 `[时间戳]` 从 871 行降到 164 行 —— 下游 prompt 少 700 多个噪声行。
- 验收：段数 ≤ 原始的 25%；总字数 ≥ 原始的 95%；抽 10 段人工读一遍没有语义断裂。

> **口径勘误（2026-09-13，落地 1C 时补）**：「总字数 ≥95%」这条如果拿**原始总字数**
> 当分母，逻辑上是自相矛盾的 —— 复读折叠本来就该丢掉那部分字。上表这组数据之所以
> 好看（99.3%），是因为实测里那 91 段复读**大多是极短的段**（段均 15 字，91 段合计
> 只占 0.7% 的字数）。遇上"整句重复 86 次"那种，按老口径算就会掉到 90% 以下，
> 被误判成"删过头"。
>
> 所以指标口径改成：**`uniqueCharRetention` = 清洗后字数 / 去重后字数 ≥ 95%**
> （判「有没有删过头」），`charRetention`（对原始字数）降为参考值不再参与判定。
> 脚本 `Scripts/quality_report.py` 已同步。

调用 1 —— 速览（输出 `headline` + `overviewBullets` + `timeline` + `decisions` + `actions` + `openQuestions`）：

```

"结论是什么、我该做什么"的同事。

硬性要求：
1. 只输出 JSON，不要 Markdown 代码围栏、不要解释。
2. 速览不是主题清单，是电梯汇报：读完必须知道 ①在解决什么问题 ②定了什么 ③下一步谁做什么。

【overviewBullets 怎么写】
- 3~6 条，按重要性排序，不按时间顺序复述。
- 每条是一个"信息"，不是一个"话题名"。
  反例："讨论了多模态"        （话题名，错）
  正例："[43:20] 多模态先做接口预留，移动端本期不做"  （信息，对）
- 决定、数字、日期、版本号优先放进前三条。

输出：{ headline, overviewBullets[], timeline[], decisions[], actions[], openQuestions[], confidence }
```

调用 2 —— 纪要（输出只要 `minutes`）：

```

要求：
- 只输出 JSON，外层键只有 minutes。
- 用 ## 议题名 分节。每节按「背景 → 讨论要点 → 结论」写，可以用有序列表。
- 写的是实质性内容（谁提了什么方案、数字是多少、为什么否掉），不是过程叙述。
- 绝对禁止：会上介绍了、会上讨论了、谈到了、提到了、围绕……展开、延伸到、中段主要围绕。
- 原文里的数字、版本号、日期、人名、系统名必须写进去。

```

- 实测依据：§2.4。改造后产出见 B1 / B2b 样例。

### 5.2 LLM 裁判（人工抽检的替代）

用**不同厂商**的模型当裁判（避免自我偏好），对每份纪要打 4 个分：

| 维度 | 问法 |
|---|---|
| 忠实度 | "以下哪一条纪要内容在逐字稿里找不到依据？逐条列出编号。" |
| 覆盖度 | "逐字稿里的 5 个关键决定，纪要覆盖了几个？列出漏掉的。" |
| 信息密度 | "这份纪要里有多少句是'谁跟谁聊了某个话题'式的废话？列出。" |
| 可执行性 | "只看这份纪要，一个没参会的人能知道明天该做什么吗？为什么？" |

**忠实度必须单独测**：摘要幻觉分"内在"（把原文信息写歪）和"外在"（补了原文没有的事实）两类，前者更危险。
传统指标（ROUGE/BLEU）对**抽象式**摘要有系统性偏差（措辞不同就判低分），不适合做验收门槛，只适合做"改前改后同向变化"的粗信号。

### 5.3 推荐做法

建一个临时 XCTest（照抄现有的 `MS_E2E_KEY` 模式）：

```
Tests/MeetingScribeTests/SummaryQualityE2ETests.swift
  读取 docs/verification/quality/*.json（逐字稿 + 金标准）
  → 跑 MeetingSummaryEngine().analyze(...)
  → 断言：5.1 表里的客观指标
  → 无 MS_E2E_KEY 时 XCTSkip
```

## 6 业界对照（2025-2026）

| 产品 | 关键做法 | 本项目的差距 |
|---|---|---|
| 飞书妙记 | 中文体验公认最好；**专业术语/热词表**、说话人分离、模板化纪要 | 缺热词表、缺说话人分离 |
| 通义听悟 | 转写 + 摘要 + 待办；本土化术语 | 缺术语表 |
| Granola | 让**用户提供会议背景**再生成；强调"自己的笔记 + AI 补充" | 无背景输入 |
| Otter.ai / Fireflies.ai | Otter 以**摘要质量**为卖点；Fireflies 强在**行动项 + 集成**（把待办推到 Slack/Asana） | 待办无 owner、无导出 |
| Read AI / Krisp | 强调"会议效率指标" | 无 |
| 通用最佳实践（WPS 官方） | 提示词三要素：**会议背景 + 结构要求（主题/要点/结论/待办及负责人/截止）+ 特殊要求（提取行动项、去口语、不确定标待确认）** | 现状 prompt **三条全缺**，还多了一条"禁止写决策与待办" |

主流产品没有一家把"纪要正文"和"结论/待办"刻意割裂开 —— 现在的 prompt 那句禁令是**本项目的独创，也是最大的自伤**。

## 7 不做什么（避免过度工程）

| 想法 | 为什么不建议 |
|---|---|
| 直接开 VAD 提升准确率 | 实测更差（段数 ×3、标点几乎全丢），见 §2.2 |
| 换更强的云端转写模型 | 与"本地优先、隐私不出机"的产品定位冲突；而 P0-1+P0-2 已能拿到大部分收益 |
| 换更大的总结模型 | 截断问题的根因是**预算**，不是模型能力；先修预算再谈换模型 |
| 引入 RAG / 向量库 | 单场会议的上下文完全放得下（21.5k 字符），不需要检索 |
| 做 4 套会议类型模板 | 先加一句方向指引（P2-3），观察用户是否真的分场景使用 |
| 让用户逐条确认决策/待办 | 先让产出**值得确认**；现在的产出用户根本不想看第二遍 |

## 8 建议的落地顺序

| 顺序 | 事项 | 依赖 | 可验证信号 |
|---|---|---|---|
| 1 | **P0-1** 逐字稿后处理 | 无 | 871→164 段，字数保留 ≥95% |
| 2 | **P0-2** 术语提示词 + `-sns` + `--carry-initial-prompt` | 无 | 标点段 100%，专名命中 ↑ |
| 3 | **P0-3** 预算 32k + 截断识别 + 宽容解析 | 无 | `finish_reason` 全 `stop` |
| 4 | **P0-4** 两段式 prompt 重写 | 与 3 同批（否则会更糟，见 §2.4 B 组） | 速览 ≥250 字、纪要 ≥1200 字、空话 0 |
| 5 | **P1-1** 数据模型加 `headline`/`overviewBullets`/`owner`/`openQuestions` | 4 | 老会话仍可解析 |
| 6 | **P1-2** 速览页重做渲染 | 5 | 一屏能看到结论 + 要点 + 待办摘要 |
| 7 | **P1-3** 术语表 UI | 2 | 用户加词后错词减少 |
| 8 | **P1-5** 材料不足门禁 | 无 | 25 秒误录不再出现元评论 |
| 9 | **5.x** 建 5 场评测集 | 4 | 指标可复算 |
| 10 | P2 系列 | 观察 1~8 后的真实效果再定 | — |

> ⚠️ **第 3 步和第 4 步必须同批上**。只改 prompt 不改预算，实测会从"截断"恶化成"完全无正文"（§2.4 B 组：0 字）。

> 本表的**执行版本**见《[质量提升执行计划](质量提升执行计划.md)》：阶段划分、验收门、
> **P0 之后的决策门（Gate A/B）**、P2 的指标触发条件、风险登记册与版本节奏。
> 两处结论不一致时以执行计划为准（其中"把建评测集提到第 1 步"是对本表的修正）。
