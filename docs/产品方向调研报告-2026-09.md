# MeetingScribe 产品方向调研报告

> 2026-09-16 · 方法：**先量家底（代码 + 项目内实测数字）→ 再看赛道（外部竞品与用户抱怨）→ 用机会-解决方案树推方向**
> 所有结论都标了出处。凡是没有证据的判断，文中明确写「**待验证**」。

---

## 0 一句话结论

**这个产品最难的仗已经打完了，但仗打完之后的东西没接上。**

它把中文会议转写里真正要命的问题都解决过了——产出被**静默截断**、prompt 把纪要写空、术语错词、
双声道分「我方/对方」、质量有可复算的尺子。这些是**别人还没解决**的硬骨头。

但产品把纪要产出来之后，就**停在了 App 里**：

- **没有导出**（源码里 `grep` 零命中）
- **没有溯源**——点一句话跳不到那段录音（`grep` 也零命中），
  而这恰恰是竞品评测反复点名的能力

所以下一步的方向**不是「再加 AI 功能」**，而是：

> **先把已经产出的东西接进用户真正的工作流，再拿「中文 + 开箱即用 + 我方/对方」这三张牌去打差异化。**

## 1 家底：真实能力与真实短板

### 1.1 已经做到的（都是项目内可复算的）

| 能力 | 现状 | 为什么这不容易 |
|---|---|---|
| **本地转写** | 本机 `whisper.cpp`，逐字稿不出机器 | 中文普通话的标点与专名是老大难 |
| **逐字稿后处理** | 复读折叠 <br>→ 术语替换 <br>→ 按句合并 <br>→ 丢低置信 | 纯确定性、**零模型成本**，是可复算的收益 |
| **术语表** | **一份数据三处消费**：<br>① whisper `--prompt` <br>② 清洗替换表 <br>③ 整理 prompt 约束 | 中文会议专名（人名/公司/项目）错一个，纪要就废一半 |
| **两段式 prompt** | 速览与纪要**并发**生成 | 修掉了「一条禁止写实质内容的 prompt 把自己掏空」这个自伤 |
| **逐字稿可就地编辑** | 改完可**一键重整理** | 人工校正过的段在后续自动替换里**原样穿过**，不会被改回去 |
| **双声道录音** | 录到麦克风 + 系统两路 → 标 **我方 / 对方** | 竞品的说话人分离要么没有、要么要额外模型 |
| **质量度量** | **13 项指标** + LLM **异厂裁判**，已进 CI | 「哪一步变好了」有数字，不靠感觉 |
| **测试** | **206 条通过** | — |

### 1.2 已知的短板（**有实测数字，不是猜的**）

| 短板 | 实测数字 | 性质 |
|---|---|---|
| **待办不可执行** | 裁判四场**一致给 2/4**，理由每次都是「待办缺责任人 / 缺时间节点」 | 产出侧问题 |
| **忠实度不足** | 裁判四场**一致给 2/4**（未达） | 产出侧问题 |
| **待办的「负责人」抽不出来** | 产出侧实得 **16%**；材料侧天花板 **22.9%**；通过率 **75%** | **材料侧天花板**（详见下） |
| **长会没验证过** | >60 min 的分章路径**零覆盖**（评测集最长 44.7 min、13037 字 < 24000 阈值） | **素材缺口**，不是「没问题」 |
| **产出出不去** | 导出功能 `grep` **零命中** | 闭环缺口 |
| **不敢核对** | 溯源跳转 `grep` **零命中** | 闭环缺口 |

> **「材料侧天花板」这个词要说清楚**：探针量出来，逐字稿里 1744 段只有 **14 段（0.8%）**
> 含指派/承接语，且其中还夹着「这个我不负责」这类否定句。
> **也就是说：会上本来就极少有人把活派到具体人头上。**
> 想靠改 prompt 把「负责人」占比做到 30%，**唯一的路是让模型编出责任人**——数字好看了，内容变假了，
> 而且**没人看得出来**。这条路不能走。

### 1.3 一个被埋没的好消息

**「点一句话跳到那段录音」这件事，数据全都已经在了，只差接线。**

| 需要的东西 | 现状 | 位置 |
|---|---|---|
| 决策/待办带时间戳 | ✅ **已有** | `MeetingModels.swift:692/702` |
| 逐字稿段带说话人 | ✅ **已有** | `MeetingModels.swift:667` |
| 播放器能定位 | ✅ **已有** `player.seek(to:)` | `WorkbenchView.swift:1035` |
| 可拖动的进度条 | ✅ **已有** `Slider` | `WorkbenchView.swift:2113` |
| 条目被点击后跳转 | ❌ **缺这一根线** | — |

**这意味着：这是几天内能做完的事，不是「新功能开发」。** 这条证据直接改变了下面的优先级排序。

## 2 赛道格局（2026 年真实情况）

### 2.1 直接竞品

| 产品 | 本地/离线 | 价格 | 强在哪 | 弱在哪 |
|---|---|---|---|---|
| **Meetily** | ✅ **100% 本地** | 开源（**30k star**） | Rust 重写 <br>实时转写 <br>多模型总结 | 要**自己配模型** <br>说话人分离在 **Pro 版**，社区版没有 |
| **AutoMinutes** | ✅ 完全离线 | 商业（有免费版） | Mac 原生 <br>本地 LLM（Qwen2.5/Llama3/Gemma/Yi）<br>**可导出录音/原文/纪要** | 要**自己下模型** <br>无「我方/对方」 |
| **MacWhisper** | ✅ 本地 | **59 欧元**（≈ 500 元） | 成熟、快 <br>100 种语言 | **贵** —— 贵到催生了「我自己写个免费替代」的项目 |
| **VoiceNotes / Buzz** | ✅ 本地 | 免费/低价 | 简单直接 | 只做转写，**不做纪要** |
| **飞书妙记 / 通义听悟 / 讯飞听见** | ❌ 必须上云 | 免费额度 + 订阅 | 中文体验最好 <br>生态集成深（自动进飞书文档/IM） | **内容必须上传** <br>企业涉密场景不敢用 |
| **Otter.ai / Fireflies.ai** | ❌ 云 | 订阅制 | Fireflies 强在**把待办推进 Slack/Asana/Notion** | 中文一般 <br>贵 <br>要上传 |

### 2.2 用户在这个赛道里真正在抱怨什么

按出现频次和情绪强度排（来源：中文技术社区的实测横评与讨论）：

| 抱怨 | 代表说法 | 谁被骂 |
|---|---|---|
| **泄密/隐私** | 「用 AI 整理会议记录导致泄密冲上热搜」<br>「**不能上传到任何第三方服务器，这是合规底线，不是偏好**」 | 所有云产品 |
| **贵** | 「MacWhisper 太贵了！用高级一点模型最少得 59 欧元，近 500 人民币」 | 商业软件 |
| **纪要不可信、没法核对** | 「真正好用的 AI 会议纪要软件，必须提供**溯源**能力：**点击纪要中的任意一句话，能直接跳转到对应的转写原文或音频时间戳**」 | 大多数产品 |
| **纪要空洞、不能用** | 需要的是「会议主题、核心观点、争议点、待办事项、**每项负责人**」 | 大多数产品 |
| **要自己折腾配置** | 开源工具普遍要自己装引擎、下模型、配路径 | 开源工具 |

### 2.3 空位在哪（MeetingScribe 可以站的地方）

| 空位 | 为什么现在没人占住 |
|---|---|
| **中文商务会的「我方 / 对方」切分** | Meetily 社区版没有说话人分离，Pro 才有；AutoMinutes 没提。<br>而中文商务会议（和客户、和供应商、和外包方）**天然就是两方对话** |
| **开箱即用** | 竞品都要用户自己下模型、配路径。<br>MeetingScribe 的包**自带 465MB 模型，解压即用** |
| **中文专名的术语表** | 竞品普遍没有「一份表三处生效」的做法 |
| **「不开源就得花钱」的中间态** | 免费、开源、MIT、可自己编译，同时**不牺牲开箱即用** |

> ⚠️ **但要诚实说一句**：Meetily 已经 30k star，**「本地 + 隐私」这个位置不是没人占**。
> 所以 MeetingScribe **不适合正面打「隐私」这张牌**——那是别人的主场。
> 它真正的差异是**中文场景的完成度**，不是「我本地我骄傲」。

## 3 用户是谁

### 3.1 主用户：**你自己**

这不是偷懒的答案，是最强的一条：

| 证据 | 说明 |
|---|---|
| 你每周有多场中文会议 | 客户会、评审会、周会（项目里已有真实会话数据） |
| 你是 PM + UI | 你自己就能判断「这份纪要能不能直接发出去」 |
| 你在意隐私与成本 | 你已经为「不上传云端」做了取舍 |
| 你已经踩过产品的坑 | 你报过「导入音频不能播」「速览纪要没出来」「失败态没入口」 |

**推论**：只要「**你自己下一场会，不再需要手工整理纪要**」，这个产品就成立了。
这比任何市场调研都硬——**因为你是最挑剔的用户，而且你不需要说服自己**。

### 3.2 次用户：中文商务场景里「不能上传」的人

| 画像 | 为什么需要 |
|---|---|
| **律师 / 法务** | 客户会谈内容涉密，且**纪要可能要当证据用**（需要溯源到原话） |
| **HR / 面试官** | 面试录音涉及个人信息 |
| **投资 / 尽调** | 被投企业的敏感信息 |
| **咨询 / 外包方** | 客户不允许内容外流，且**要交付纪要** |
| **医疗 / 心理** | 极其敏感 |

这五类人的共同点：**「不能上传」是硬约束，不是偏好**；而且**「纪要要能被核对」是刚需**。

### 3.3 不是谁

| 不是 | 原因 |
|---|---|
| 需要 3 人以上区分具体发言人 | 要引 Python 运行时（pyannote 那类），与「纯本机 Swift」定位冲突 |
| 需要英文为主的会议 | 竞品（MacWhisper / Meetily）已经覆盖得很好 |
| 需要把纪要自动推进 Slack/Notion/飞书 | 集成是重工程，且云产品在这件事上有天然优势 |

## 4 机会排序（用户视角的「问题」，不是「功能」）

打分说明：**重要度**（这事对用户多重要）× **满足度**（现在市面/本产品解决得多好），
`机会分 = 重要度 × (1 − 满足度)`，两项都归一到 0~1。**分越高越值得做**。

| # | 机会（用户的话） | 重要度 | 满足度 | 机会分 | 判定 |
|---|---|---|---|---|---|
| O1 | 「**我整理好的纪要送不出去**，还得自己复制粘贴到文档/群里」 | 0.9 | 0.1 | **0.81** | 🔴 **最高** |
| O2 | 「**我不敢直接用它写的纪要**，万一哪句写错了呢？」 | 0.9 | 0.2 | **0.72** | 🔴 **很高** |
| O3 | 「待办**没写谁负责、没写什么时候**，等于没写」 | 0.8 | 0.3 | 0.56 | 🟠 高（有天花板） |
| O4 | 「**一小时的会它处理得怎么样**，我心里没底」 | 0.6 | 0.2 | 0.48 | 🟠 中高（待验证） |
| O5 | 「我不想把会议内容传到别人服务器」 | 0.9 | 0.8 | 0.18 | 🟢 **已解决**（本产品就是干这个的） |
| O6 | 「**装的时候被系统拦住**，折腾半天」 | 0.5 | 0.3 | 0.35 | 🟡 中（99 美元可解） |
| O7 | 「订阅费太贵」 | 0.7 | 0.9 | 0.07 | 🟢 **已解决**（免费开源） |

**关键读数**：

- **`O1` 和 `O2` 是断层级的高分**——它们不但是用户最疼的，而且**我们自己解决得最差**。
- **`O5`/`O7` 分数低不是因为不重要，而是因为我们已经做到了。** 这两条是**守住的成绩**，不是方向。
- **`O3` 有天花板**：材料侧上限 22.9%，做到满分也只有 0.56×——所以它**不适合当第一优先级**，
  而且**验收标准不能写成「负责人占比 ≥30%」**（写这条等于给自己埋一个必然不达标的坑）。

## 5 机会-解决方案树（OST）

**期望结果（Outcome）**——用一句可测的话：

> ### 「一场会议录完，我**不做二次加工**就能把它发出去。」

可量化口径：**从录音结束 → 纪要发到目标位置，人工操作次数 ≤ 1 次**。

```
Outcome：录完不做二次加工就能发出去
│
├─ O1 拿不出去（机会分 0.81）
│   ├─ S1 导出 Markdown / 纯文本（含决策+待办+时间戳）
│   ├─ S2 一键复制全文到剪贴板（发群里用）
│   ├─ S3 导出逐字稿为 SRT / TXT（做字幕、存档用）
│   └─ S4 导出「待办清单」为可勾选格式（.md checkbox / .ics 日历）
│
├─ O2 不敢信（机会分 0.72）
│   ├─ S5 点纪要/待办 → 跳到对应音频位置（**数据已具备，只差接线**）
│   ├─ S6 逐字稿播放高亮跟随（放到哪句，哪句亮）
│   ├─ S7 每条结论后面带原话时间戳（可点）
│   └─ S8 「置信度」从数字改成看得懂的措辞
│
├─ O3 待办不落地（机会分 0.56，**受材料天花板限制**）
│   ├─ S9 待办导出后允许你手工补负责人（**人补，不让模型编**）
│   ├─ S10 「负责人」只在逐字稿**真的点名**时才填，没点就留空并标「未指派」
│   └─ S11 双声道把「你负责」这句话变成可判定（做完了，待人工外放自测）
│
├─ O4 长会没底（机会分 0.48，**素材缺口**）
│   └─ S12 造一段 60min+ 的中文会议素材，把分章路径跑到真实覆盖
│
└─ O6 装不上（机会分 0.35，**要花钱**）
    └─ S13 Developer ID 签名 + Apple 公证（99 美元/年）
```

## 6 建议的升级路线

### 第一步：**把闭环接上**（1~2 天，纯接线，零架构风险）

| 做什么 | 为什么是它 | 完成判据 |
|---|---|---|
| **导出 Markdown / 纯文本** | O1 最高分 | 导出的文件能在**飞书文档 / 腾讯文档 / Notion** 里直接粘贴且格式不乱 |
| **一键复制全文** | 发群里的真实动作就是「复制」 | 一次点击，剪贴板里是完整纪要 |
| **点纪要/待办 → 跳音频** | **数据全在，只差接线** | 点概览里任意一条，播放器跳到对应秒数并开始播 |
| **逐字稿播放跟随** | 核对时最自然的动作 | 播放时当前句自动高亮、自动滚动 |

> **为什么第一步是它而不是「优化纪要质量」**：
> 因为**质量优化得再好，用户拿不出去也感知不到**。
> 而且 —— 这个判断是有代价的教训：项目此前已经投入了**阶段 0~4 一整套质量工程**
> （造尺子 → P0 止血 → 度量固化 → P2 触发），质量确实上去了，
> **但产出仍然困在 App 里**。这是典型的「优化了过程，没优化结果」。

### 第二步：把「我方 / 对方」变成纪要里的可判定表述（1~2 周）

| 做什么 | 判据 |
|---|---|
| 完成**双声道人工外放自测** | 逐字稿每段带 `speaker`，**人工抽查 20 段标注正确** |
| 纪要出现**可判定的跨方表述** | 写出「我方要求对方…」「对方确认…」，而不是「会上讨论了…」 |
| 待办按「我方要做的 / 对方要做的」分组 | 导出后能直接分派 |
| **造 60min+ 素材，跑分章路径** | 分章路径从「零覆盖」变成「有覆盖」 |

### 第三步：让别人也能用（需要你的资源）

| 做什么 | 卡在哪 |
|---|---|
| **Developer ID + 公证** | Apple Developer Program，99 美元/年 |
| 找 3~5 个真实用户试用 | 用第二步的判据收反馈 |

### 版本节奏建议

| 版本 | 内容 |
|---|---|
| `v0.11` | 第一步（导出 + 溯源跳转 + 播放跟随） |
| `v0.12` | 第二步（双声道验收 + 跨方表述 + 长会覆盖） |
| `v1.0` | 第三步（公证 + 真实用户验证通过） |

## 7 明确不做（避免过度工程）

| 想法 | 为什么不建议 |
|---|---|
| **加 3 人以上说话人分离** | 要引 Python 运行时（pyannote 一类），与「纯本机 Swift」定位冲突；<br>且**没有需求信号**（Gate B 第 5 条未命中） |
| **换云端转写模型** | 与「内容不出机器」的定位**正面冲突**——这是产品的地基，不是可选项 |
| **做实时转写** | 要改架构；且 Meetily 已经占住这个位置（4 倍速、实时） |
| **引 RAG / 向量库** | 单场会议上下文**完全放得下**（实测 21.5k 字符），不需要检索 |
| **让模型「推断」责任人** | 材料侧天花板 22.9%，硬推的唯一结果是**编造**。<br>数字好看，内容变假，**且没人看得出来** |
| **做 4 套会议类型模板** | 先观察到用户**真的**按「周会/客户会/评审会」提不同要求，再做 |
| **让用户逐条确认决策/待办** | 先让产出**值得确认**——现在的产出用户根本不想看第二遍 |

## 8 验证它的第一步（今天就能做）

**不要再做功能了，先做一次真实的自我验证。**

| # | 动作 | 要记的数 |
|---|---|---|
| 1 | 找**你最近一场真实会议**（客户会或评审会最好），用当前版本从头走一遍：录 → 转 → 看速览 → 看纪要 | — |
| 2 | 试着把它**发到它该去的地方**（工作群 / 文档 / 待办工具） | **你手工操作了几次？** |
| 3 | 回看纪要时，有没有哪一句你想**核对原话** | **你核对了没？怎么核对的？** |
| 4 | 数一下纪要里**你真正会用**的内容有几条 | **有用条数 / 总条数** |

**判读规则（先写好，免得做完又误判）**：

| 观察到的 | 结论 | 下一步 |
|---|---|---|
| 手工操作 **≥ 3 次**，或卡在「复制不出去」 | O1 成立 | 立刻做第一步 |
| 有想核对但**没核对成**（要去逐字稿里翻） | O2 成立 | 立刻做第一步 |
| 有用条数 / 总条数 **< 50%** | 质量仍是瓶颈 | 先做质量，再做闭环 |
| 以上都不明显 | **说明我把问题想重了** | 回来重新看用户是谁 |

> **最后一句提醒**：这份报告的价值不在于列了多少条建议，
> 而在于它把「下一步做什么」从**感觉**变成了**可以被打脸的判据**。
> 上面那张判读表就是用来打脸的——如果做完发现「其实不卡」，那就说明方向要换。
